## Overview

[OpenCode](https://opencode.ai/) is an open-source AI coding agent. You can use it as a CLI or run it as a server and drive sessions from your own code to build products on top of the agent. Laminar makes those runs observable with the `@lmnr-ai/opencode-plugin` plugin, which works with OpenCode V2 and with OpenCode V1 (1.4 and newer).

What Laminar captures:

- Every conversation turn, one trace per turn.
- LLM prompts, responses, token counts, latency, and cost.
- Tool calls (`bash`, `read`, `write`, `edit`, custom tools) with arguments and results.
- Subagents, nested under the tool call that started them.
- Optionally, when you send a prompt from inside `observe`, the turn nests under your caller span, so your code and the agent's work land in a single trace.

Each trace carries the OpenCode session ID as its Laminar session ID, so every turn in the same OpenCode conversation shows up under one session in Laminar.

## Set up the plugin

Setup is two steps: add the plugin to your OpenCode config and set your Laminar project API key. That traces every turn, whether it comes from the TUI, `opencode run`, `opencode serve`, or a client talking to the server.

<Steps>
<Step title="Add the Laminar plugin to your OpenCode config">

The plugin is what actually emits the turn and tool spans. Add it to the OpenCode config in your project. The key differs between versions:

<Tabs>
  <Tab title="OpenCode V2">

```json opencode.jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "plugins": ["@lmnr-ai/opencode-plugin"]
}
```

  </Tab>
  <Tab title="OpenCode V1">

```json opencode.json
{
  "$schema": "https://opencode.ai/config.json",
  "plugin": ["@lmnr-ai/opencode-plugin"]
}
```

  </Tab>
</Tabs>

V2 reads `plugins` and V1 reads `plugin`. Using the other version's key means the plugin never loads.

<Note>
OpenCode reads config from several locations, and a file in the current project takes precedence over the global one in `~/.config/opencode/`. If you want tracing on by default everywhere, put the plugin entry in the global file. See OpenCode's plugin docs for [V2](https://opencode.ai/v2/docs/plugins/) and [V1](https://opencode.ai/docs/config/#plugins) for the full rules.
</Note>

</Step>
<Step title="Set LMNR_PROJECT_API_KEY">

The plugin runs inside OpenCode, so the key must be set where OpenCode runs, not in your application: export it in the shell where you start `opencode` or `opencode serve`, or put it in a `.env` file in the project directory. On V1, `opencode.createOpencode()` starts the server from your TypeScript process, so there it is the same shell.

```bash
export LMNR_PROJECT_API_KEY=your-laminar-project-api-key
```

<GetProjectApiKey />

<Tip>
Self-hosting Laminar? Also set `LMNR_BASE_URL` and `LMNR_GRPC_PORT` to point at your instance. For the OSS default, that's `http://localhost` and `8001`. On V2 you can instead pass `projectApiKey` and `baseUrl` as plugin options: `{ "package": "@lmnr-ai/opencode-plugin", "options": { "baseUrl": "..." } }` in place of the plain plugin name.
</Tip>

</Step>
</Steps>

## Using the OpenCode CLI

With the plugin configured, run OpenCode as usual. If you don't have it yet, follow [OpenCode's install guide](https://opencode.ai/docs/#install). You don't need to install the plugin package yourself; OpenCode resolves it from npm.

```bash
opencode
```

When the plugin starts, it logs `[laminar] tracing initialized → https://api.lmnr.ai` on V2, or `Laminar tracing initialized → https://api.lmnr.ai` on V1. On V1 the plugin also turns on OpenCode's experimental OpenTelemetry flag for you, so you don't need to touch the OTel config. V2 doesn't have that flag, and the plugin builds its spans from OpenCode's event stream instead.

Each turn becomes its own top-level trace:

## Nest turns under your own spans (optional)

If you drive OpenCode from your own code, you can make each turn a child of a span in your application, so your code and the agent's work land in one trace. Without this, every turn is still traced, just as its own top-level trace.

The prompt carries your current span context to OpenCode, and the plugin parents the turn under it:

- **V2:** pass the context as `lmnrSpanContext` in the prompt's `metadata`. This works with any way of sending prompts: `@opencode/client`, `@opencode/sdk`, or a plain HTTP request to the server. The example uses `@opencode/client`.
- **V1:** `@lmnr-ai/lmnr` patches `@opencode-ai/sdk` and injects the context into every `client.session.prompt` call made inside `observe`.

<Tabs>
  <Tab title="OpenCode V2">

Install the Laminar SDK and OpenCode's [JavaScript client](https://opencode.ai/v2/docs/build/client/), and start the server with `opencode serve`:

```bash
npm install @lmnr-ai/lmnr@latest @opencode/client@latest
```

Pass the current span context as `lmnrSpanContext` in the prompt's `metadata`:

```typescript {1,4,11,15,21}
import { Laminar, observe } from "@lmnr-ai/lmnr";
import { OpenCode } from "@opencode/client";

Laminar.initialize();

const client = OpenCode.make({ baseUrl: "http://localhost:4096" });
const session = await client.session.create({
  location: { directory: "/workspace" },
});

await observe({ name: "my-agent-step" }, async () => {
  await client.session.prompt({
    sessionID: session.id,
    text: "Create a Python factorial function and test it.",
    metadata: { lmnrSpanContext: Laminar.serializeLaminarSpanContext() },
  });
  // Wait for the turn to finish so it stays inside this span.
  await client.session.wait({ sessionID: session.id });
});

await Laminar.shutdown();
```

  </Tab>
  <Tab title="OpenCode V1">

Install the Laminar SDK and `@opencode-ai/sdk`:

```bash
npm install @lmnr-ai/lmnr@latest @opencode-ai/sdk@latest
```

Initialize Laminar with the `opencode` module:

```typescript {1,2,5-9,16}
import * as opencode from "@opencode-ai/sdk";
import { Laminar, observe } from "@lmnr-ai/lmnr";

// Initialize Laminar once at the entry point.
Laminar.initialize({
  instrumentModules: {
    opencode,
  },
});

const { client, server } = await opencode.createOpencode();

try {
  const sessionRes = await client.session.create({ body: { title: "agent run" } });

  await observe({ name: "my-agent-step" }, async () => {
    await client.session.prompt({
      path: { id: sessionRes.data.id },
      body: {
        model: { providerID: "anthropic", modelID: "claude-haiku-4-5" },
        parts: [{ type: "text", text: "Create a Python factorial function and test it." }],
      },
    });
  });
} finally {
  server.close();
  await Laminar.shutdown();
}
```

<Note>
If you import `@opencode-ai/sdk` before `Laminar.initialize()` (common when the project has `"type": "module"` in `package.json`), your local reference won't be auto-wrapped. Pass the module via `instrumentModules` as shown above; the instrumentation attaches to the SDK's `Session` class and every new `OpencodeClient` picks it up.
</Note>

  </Tab>
</Tabs>

## Trace structure

Because your prompt hands the span context to the server-side plugin, the trace comes back as a single tree: your `observe` span is the root, the server's turn span is its child, and every model call and tool call hangs off the turn. There is no separate trace for the server: everything the OpenCode process does on this turn shows up nested under the TypeScript code that kicked it off.

On V2 the turn span is `opencode turn` and each model call is an `ai.llm <provider>:<model>` span. The screenshots below come from a V1 run, where the turn wraps `session.llm` spans instead.

## Track outcomes with Signals

Traces answer *what happened on this turn*. **[Signals](/signals/introduction) answer the cross-trace question**: *how often does the agent edit a file it wasn't asked to, when does the bash tool run a destructive command, which turns burn tokens without touching a file*. A Signal pairs a plain-language prompt with a JSON output schema. Laminar runs it live on new traces (Triggers) or backfills it across history (Jobs) and records a structured event every time it matches. From there you [query](/platform/sql-editor), [cluster](/signals/clusters), and [alert](/signals/alerts) on events across every trace.

<Note>
Every new project ships with a **Failure Detector** Signal that categorizes issues on any trace over 1000 tokens. Open it from the Signals sidebar to see events as soon as your OpenCode traces arrive.
</Note>

## Query across traces

- **[SQL editor](/platform/sql-editor)** for ad-hoc queries across traces, spans, signals, and evals.
- **SQL API** for programmatic access from scripts and pipelines.
- **[CLI](/platform/cli)** (`lmnr-cli sql query`) for terminal-driven queries and piping JSON into shell tools or coding agents.
- **[MCP server](/platform/mcp)** to query Laminar directly from OpenCode, Claude Code, Cursor, or Codex.

## Troubleshooting

<AccordionGroup>
  <Accordion title="I don't see any traces in Laminar">
    - `LMNR_PROJECT_API_KEY` must be set in the environment of the process that launches the OpenCode server, not just in the process that creates the OpenCode client. The plugin runs on the server side and reads the key there.
    - Check the OpenCode log for `tracing initialized → ...`. If you see `LMNR_PROJECT_API_KEY not set` instead, the plugin loaded but had no key.
    - Check the config key for your OpenCode version: V2 reads `"plugins"`, V1 reads `"plugin"`. The other version's key silently does nothing.
  </Accordion>
  <Accordion title="Traces from my TypeScript caller aren't linked to the server turn">
    - Make sure both sides are on a current `@lmnr-ai/lmnr` (install with `@latest`). The caller-side instrumentation and the plugin's context extraction need to match up.
    - The server process also needs the plugin in its OpenCode config. Without it, only your caller-side span reaches Laminar.
    - Send the prompt from inside `observe` (or another active span). There is no context to pass otherwise.
    - On V2, pass `metadata: { lmnrSpanContext: Laminar.serializeLaminarSpanContext() }` with the prompt. Only V1's `@opencode-ai/sdk` gets the context injected automatically.
  </Accordion>
  <Accordion title="Self-hosting Laminar">
    Export `LMNR_BASE_URL` and `LMNR_GRPC_PORT` in the same environment as `LMNR_PROJECT_API_KEY`. For a local OSS instance, that's `LMNR_BASE_URL=http://localhost` and `LMNR_GRPC_PORT=8001`. The plugin passes these through when it initializes Laminar.
  </Accordion>
</AccordionGroup>
