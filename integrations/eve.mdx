## Overview

Laminar is an open-source, OpenTelemetry-native observability platform for AI agents. Trace, debug, and monitor every run of an [eve](https://eve.dev/docs/introduction) durable agent by adding Laminar as an OpenTelemetry destination. eve emits spans for agent turns, model calls, and tool calls; Laminar captures the full run without per-call wiring. Self-host via Helm or use managed cloud.

What Laminar captures from an eve agent:

- User messages and system instructions sent to the model.
- Model output and reasoning for each turn.
- Tool calls, their arguments, and tool results.
- Token counts, latency, and cost per call.
- The model name and provider behind each call.

eve uses the AI SDK's OpenTelemetry support under the hood, so its spans follow the GenAI semantic conventions. Laminar reads those directly and renders the run as a transcript: the user question, each model turn, tool calls, and the final answer, in order.

## Getting Started

eve discovers files under `agent/instrumentation/` automatically. Add a Laminar destination using eve's `otelIntegration()`; eve owns the tracer provider and the agent's trace context. This setup requires `@lmnr-ai/lmnr` 0.8.51 or newer and eve 0.76.3 or newer (Node.js 24). If upgrading an older agent, see [Migrate from legacy eve instrumentation](#migrate-from-legacy-eve-instrumentation).

<Steps>
<Step title="Install">

```bash
npm install @lmnr-ai/lmnr@latest eve@latest
```

The agent does not need `@vercel/otel` for this integration. eve registers its own OpenTelemetry pipeline.

</Step>
<Step title="Set environment variables">

```bash
# .env
LMNR_PROJECT_API_KEY=your-laminar-project-api-key
```

<GetProjectApiKey />

</Step>
<Step title="Add Laminar as an OpenTelemetry destination">

Create `agent/instrumentation/laminar.ts`. eve discovers the file and attaches Laminar's span processor to its OpenTelemetry pipeline. The processor reads `LMNR_PROJECT_API_KEY` from the agent's environment.

```typescript agent/instrumentation/laminar.ts {1-2,4-6}
import { LaminarSpanProcessor } from "@lmnr-ai/lmnr";
import { otelIntegration } from "eve/instrumentation/otel";

export default otelIntegration({
  spanProcessors: [new LaminarSpanProcessor()],
});
```

Do not call `Laminar.initialize()` in the agent: eve owns the tracer provider. A separate `otel.ts` file is only needed if you want process-wide settings such as sampling or a content-capture policy.

<Note>
Set `LMNR_PROJECT_API_KEY` in the **agent server's** environment, not just the eval runner's. The agent exports its own spans; the reporter exports the eval grades separately.
</Note>

</Step>
<Step title="Run your agent">

Build and start the agent as usual. Every turn is traced.

```bash
eve build
eve start
```

Send the agent a message and the trace appears in Laminar.

</Step>
</Steps>

## Keeping payloads off your spans

eve's default OpenTelemetry policy records prompts and responses in development and public conversations. Private conversations in preview or production are metadata-only. To exclude content for **all** OpenTelemetry destinations, add a process-wide policy in `agent/instrumentation/otel.ts`. Token counts, latency, and cost remain available.

```typescript agent/instrumentation/otel.ts {1,3-8}
import { otel } from "eve/instrumentation/otel";

export default otel({
  tracePolicy: () => ({
    emit: true,
    recordInputs: false,
    recordOutputs: false,
  }),
});
```

This policy is a capture ceiling: a destination cannot restore content excluded here. Leave `agent/instrumentation/laminar.ts` in place to export the remaining spans.

## Run evals

eve ships its own eval runner (`eve eval`). Add Laminar as a reporter to see each run as an [evaluation](/evaluations/introduction), with one datapoint per eval. You can [compare runs](/evaluations/comparing-runs) and chart scores across a group.

Use eve 0.76.3 or newer with `@lmnr-ai/lmnr` 0.8.51 or newer.

<Steps>
<Step title="Register the Laminar reporter">

Add `LaminarReporter` to the `reporters` array in your eval config. The reporter reads `LMNR_PROJECT_API_KEY` from the environment.

```typescript evals/evals.config.ts
import { LaminarReporter } from "@lmnr-ai/lmnr";
import { defineEvalConfig } from "eve/evals";

export default defineEvalConfig({
  reporters: [
    new LaminarReporter({
      name: "weather-agent",
      groupName: "weather-agent",
    }),
  ],
});
```

`groupName` is what makes runs comparable: every run under the same group appears on one progression chart. On run start the reporter prints the URL of the evaluation to stdout.

</Step>
<Step title="Run the evals">

```bash
eve eval
```

Each eval writes a datapoint as soon as eve grades it. Open the URL the reporter printed to see the scores, the assertion detail, and the trace behind each row.

</Step>
</Steps>

### Trace the judge model calls

`t.judge(...)` assertions run in the runner process, not in the agent, so the agent's instrumentation never sees them. To capture the judge's model call, register Laminar's AI SDK telemetry in the eval config. eve calls the AI SDK's `experimental_decide` from inside its own bundle, and AI SDK v7 reads registered telemetry from a global registry, so this one registration reaches it.

```typescript evals/evals.config.ts {1-2,5}
import { LaminarAiSdkTelemetry, LaminarReporter } from "@lmnr-ai/lmnr";
import { registerTelemetry } from "ai";
import { defineEvalConfig } from "eve/evals";

registerTelemetry(new LaminarAiSdkTelemetry());

export default defineEvalConfig({
  reporters: [new LaminarReporter({ name: "weather-agent" })],
});
```

That one line is the whole setup. Judge spans and eval spans share a single tracer provider in the runner: whichever of the reporter or the telemetry integration runs first initializes it, and the other reuses it. The reporter flushes it when the run finishes, so nothing is lost to the `process.exit()` that ends `eve eval`.

Each judge call lands as its own span under the eval trace. Without this step the scores are still recorded; only the judge's model call is missing.

### What lands on each datapoint

Every eval produces one datapoint with three scores:

| Score | Value |
| --- | --- |
| `eve.verdict.passed` | 1 when eve's verdict for the eval is `passed` |
| `eve.gates.passed` | 1 when every gate assertion passed |
| `eve.soft_thresholds.passed` | 1 when every soft assertion with a threshold passed |

The scores stay the same across every eval file on purpose. eve eval files assert different things, and per-assertion score columns would leave most rows empty.

Per-assertion detail goes to the datapoint metadata under `assertions`, with a shorter `failedAssertions` list when something fails. The metadata also carries the eve verdict, the session status, the eve session id, the model id, and the tools the agent called. On the trace itself, each assertion becomes an `EVALUATOR` span, so you read the grade and the run that earned it in one place.

### Reporter options

| Option | Default | Description |
| --- | --- | --- |
| `name` | eve run name | Name of the Laminar evaluation created for the run. |
| `groupName` | none | Group the run belongs to. Runs in one group share a progression chart. |
| `metadata` | none | Extra metadata attached to the evaluation. |
| `projectApiKey` | `LMNR_PROJECT_API_KEY` | Project API key. |
| `baseUrl` | `https://api.lmnr.ai` | Laminar API base URL. Set this for self-hosted Laminar. |

## Migrate from legacy eve instrumentation

Older eve agents used a single `agent/instrumentation.ts` file with `defineInstrumentation({ setup: ...registerOTel(...) })`. The old Laminar reporter patched eve's `ClientSession.send` to inject a `traceparent` header; an agent configured with `traceChannelRequests: true` could attach its spans to the runner's trace. The 0.8.51 reporter no longer patches requests. **Upgrading only Laminar while keeping eve 0.29.x detaches the eval datapoint from the agent's trace**, even though the agent's LLM spans are still exported and the eval passes.

To migrate:

1. Upgrade eve to 0.76.3 or newer and Laminar to 0.8.51 or newer.
2. Remove `agent/instrumentation.ts`. Create the `agent/instrumentation/laminar.ts` destination shown above. `@vercel/otel` and `registerOTel` are not needed for Laminar.
3. Move custom sampling or input/output policy into `agent/instrumentation/otel.ts`. If other requests still need inbound channel spans, move `traceChannelRequests: true` there too; eval linking does not require it.
4. Remove `propagateTraceContext` from the reporter config. It is deprecated and ignored in 0.8.51.

Your agent's model can stay the same. Check eval assertions when upgrading eve: assert against the completed turn (`const turn = await t.send("..."); turn.messageIncludes("expected")`) rather than reading `t.reply`. See [eve's instrumentation migration guide](https://eve.dev/docs/observability/instrumentation-migration) for other custom instrumentation.

## Track outcomes with Signals

Traces answer *what happened on this run*. **[Signals](/signals/introduction) answer the cross-trace question**: *how often does the agent call a tool that returns an empty result, when does a turn run more steps than expected, how often does the agent answer without calling the tool it should have*. A Signal pairs a plain-language prompt with a JSON output schema. Laminar runs it live on new traces (Triggers) or backfills it across history (Jobs) and records a structured event every time it matches. From there you [query](/platform/sql-editor), [cluster](/signals/clusters), and [alert](/signals/alerts) on events across every run.

<Note>
Every new project ships with a **Failure Detector** Signal that categorizes issues on any trace over 1000 tokens. Open it from the Signals sidebar to see events as soon as your eve traces arrive.
</Note>

## Troubleshooting

<AccordionGroup>
  <Accordion title="I don't see any traces in Laminar">
    - Confirm `LMNR_PROJECT_API_KEY` is set in the agent server's environment, not just the eval runner's.
    - Confirm `agent/instrumentation/laminar.ts` default-exports `otelIntegration({ spanProcessors: [new LaminarSpanProcessor()] })` and that you restarted or rebuilt the agent after editing it.
    - Check that the agent and reporter use the same project key. On an existing Vercel deployment, check its tracing sampling settings too: an unsampled agent trace cannot be exported.
  </Accordion>
  <Accordion title="I see the model and tool calls but no message content">
    Check `otel({ tracePolicy })` in `agent/instrumentation/otel.ts`. eve captures content by default in development and public conversations, but private conversations in preview or production are metadata-only. A policy that sets `recordInputs` or `recordOutputs` to `false` excludes that content for every OpenTelemetry destination.
  </Accordion>
  <Accordion title="My eval datapoints link to a trace with no agent work in it">
    Check the datapoint's `metadata.traceResolution`: `eve-native` means the reporter used a context from eve, while `reporter-fallback` means it received no usable context and created a separate trace for the grades. An agent can still export LLM spans to Laminar when its eval datapoint uses the fallback trace.

    If you upgraded `@lmnr-ai/lmnr` to 0.8.51 but kept eve 0.29.x, [migrate to eve's native instrumentation](#migrate-from-legacy-eve-instrumentation). Check that `agent/instrumentation/laminar.ts` exports the agent spans to the same project as the reporter. `traceChannelRequests`, `WORKFLOW_TRACE_MODE`, and the ignored `propagateTraceContext` option do not restore the old reporter patch.
  </Accordion>
  <Accordion title="I see the eval scores but no judge model call">
    Add `registerTelemetry(new LaminarAiSdkTelemetry())` to `evals/evals.config.ts`. Judge assertions run in the eval runner, which the agent's instrumentation never sees.
  </Accordion>
  <Accordion title="A running eval row stays pending in the UI">
    Reload the evaluation page. Rows written by the eve reporter do not stream their result into an open page yet. The stored data is complete, so a reload shows every score.
  </Accordion>
  <Accordion title="I see two tracer providers or duplicated spans">
    Remove `Laminar.initialize()` and any `registerOTel()` setup from the agent. eve owns its tracer provider and attaches `agent/instrumentation/laminar.ts` to it; adding another provider can duplicate or detach spans.

    This does not apply to `evals/evals.config.ts`. That file runs in the eval runner, where the reporter and the AI SDK telemetry integration share one provider.
  </Accordion>
</AccordionGroup>
