## FAQ

Fixes for the most common problems when running [agent evaluations](/agent-evaluations/introduction) with `lmnr-cli eval run`.

<AccordionGroup>
  <Accordion title="A change to the app or the image doesn't show up">
    `lmnr-cli` rebuilds the `lmnr.yaml` images on every run, but Docker's layer cache can still hide a change, for example a `RUN` step that downloads "latest". Check the file inside a running container, then clear the cache with `docker builder prune` or bump a cache-busting `ARG` placed before the stale step.
  </Accordion>
  <Accordion title="The app can't see an env var from harbor.yaml">
    `agents[].env` reaches every command the agent runs. If the start script launches the app with `env -i`, it must forward each name explicitly.
  </Accordion>
  <Accordion title="The trial trace has no LLM or tool calls">
    Either the app isn't instrumented with Laminar, or it didn't receive `LMNR_TRAJECTORY_PATH`. See [Capture the trajectory](/agent-evaluations/trajectories).
  </Accordion>
  <Accordion title="Job output shows [REDACTED] in odd places">
    A secret's value is very short, so every occurrence of it in the output is redacted. Use long, distinctive placeholder values.
  </Accordion>
  <Accordion title="Where are the logs for a failed trial?">
    For local runs, in `evals/<dataset>/jobs/<timestamp>/`. For `--remote` runs, open the evaluation in Laminar, select the trial, and open its **Files** tab: Harbor's output for the trial is in `trial output/`, uploaded when the dataset's run ends.

    Each trial has `agent/` (your logs and `result.json`), `verifier/` (`reward.txt`, `test-stdout.txt`), and `exception.txt` with the agent's traceback if it raised.
  </Accordion>
  <Accordion title="harbor.yaml sets datasets or tasks (exit code 16)">
    An eval dataset always runs the tasks in its own `tasks/` folder, so remove `datasets` and `tasks` from its `harbor.yaml`. To run some of the tasks, pass `--task <glob>`. For another set of tasks, create a second dataset folder next to the first.
  </Accordion>
  <Accordion title="evals/lmnr.yaml is no longer read (exit code 16)">
    `lmnr.yaml` belongs in each dataset folder, next to `harbor.yaml`. Move its images into the `lmnr.yaml` of every dataset that uses them, rewrite `dockerfile` and `context` relative to that dataset's folder (for example, `context: ..` becomes `context: ../..`), and delete the file at the root of `evals/`.
  </Accordion>
  <Accordion title="The run warns that tasks differ from lmnr.lock">
    You edited tasks since the last pull or push, so the run reports to `<dataset> unversioned` instead of the version's group. Run `lmnr-cli eval status` to list the changes. Version them with `lmnr-cli eval push`, or go back to the pinned version with `lmnr-cli eval pull --force`, which discards the edits.
  </Accordion>
  <Accordion title="eval pull refuses to overwrite local changes (exit code 22)">
    `tasks/` changed since the last pull or push, and the pull would overwrite those changes. Nothing was touched, in any dataset. Push the changes with `lmnr-cli eval push`, or discard them with `lmnr-cli eval pull --force`.
  </Accordion>
  <Accordion title="eval push says tasks/ is older than lmnr.lock (exit code 23)">
    `lmnr.lock` pins a newer version than the one `tasks/` was synced to, usually because a teammate pushed and their `lmnr.lock` came in with `git pull`. Pushing would drop their changes. Run `lmnr-cli eval pull` first. If you have edited tasks too, copy the changed task folders somewhere else, run `lmnr-cli eval pull --force`, copy them back, and push. See [Work on a dataset as a team](/agent-evaluations/eval-datasets#work-on-a-dataset-as-a-team).
  </Accordion>
  <Accordion title="The eval dataset or version isn't in Laminar (exit code 24)">
    The version `lmnr.lock` pins doesn't exist in the project `lmnr-cli` talks to. Check that `LMNR_PROJECT_API_KEY`, or the project linked with `lmnr-cli setup`, belongs to the project where the dataset was pushed.
  </Accordion>
</AccordionGroup>
