## FAQ

Fixes for the most common problems when running [agent evaluations](/agent-evaluations/introduction) with `lmnr-cli eval run`.

<AccordionGroup>
  <Accordion title="A change to the app or the image doesn't show up">
    `lmnr-cli` rebuilds the `eval.yaml` images on every run, but Docker's layer cache can still hide a change, for example a `RUN` step that downloads "latest". Check the file inside a running container, then clear the cache with `docker builder prune` or bump a cache-busting `ARG` placed before the stale step.
  </Accordion>
  <Accordion title="The app can't see an env var from eval.yaml">
    `job.agents[].env` reaches every command the agent runs. If the start script launches the app with `env -i`, it must forward each name explicitly.
  </Accordion>
  <Accordion title="The trial trace has no LLM or tool calls">
    Either the app isn't instrumented with Laminar, or it didn't receive `LMNR_TRAJECTORY_PATH`. See [Capture the trajectory](/agent-evaluations/trajectories).
  </Accordion>
  <Accordion title="Job output shows [REDACTED] in odd places">
    A secret's value is very short, so every occurrence of it in the output is redacted. Use long, distinctive placeholder values.
  </Accordion>
  <Accordion title="Where are the logs for a failed trial?">
    For local runs, in `evals/<set>/jobs/<timestamp>/`. For `--remote` runs, open the trial in Laminar and switch to its **Log** tab, which shows Harbor's output for the trial once its task set finishes.

    Each trial has `agent/` (your logs and `result.json`), `verifier/` (`reward.txt`, `test-stdout.txt`), and `exception.txt` with the agent's traceback if it raised.
  </Accordion>
  <Accordion title="Push or pull fails with exit code 22 (merge_conflict)">
    Someone else changed a task that you also changed locally, so `lmnr-cli` can't merge it, and it stopped before writing anything. Move your copy of that task out of `tasks/`, run `lmnr-cli eval pull <set>`, then re-apply your edit and push again. See [Task sets](/agent-evaluations/task-sets#publish-a-task-set).
  </Accordion>
  <Accordion title="A task is rejected because it has environment/Dockerfile">
    Tasks can't build their own image. Move the Dockerfile into the task set's scripts, add it to `images` in `eval.yaml`, and set `docker_image` in the task's `task.toml`. Keep only the case's data in `environment/`. See [the evals folder](/agent-evaluations/evals-folder).
  </Accordion>
  <Accordion title="The run warns that my copy is based on a different version than the pin">
    Your local copy in `tasks/` and the version `eval.yaml` pins have drifted apart. The run still uses your local copy. Run `lmnr-cli eval pull <set>` to merge the latest version in, or bump `version` in `eval.yaml` after you push.
  </Accordion>
  <Accordion title="The run fails because the task set has no eval.yaml (exit code 23)">
    `lmnr-cli eval run` only uses scripts from your repo. If they were written elsewhere, for example by the Laminar agent, run `lmnr-cli eval pull <set>` to fetch the scripts the task set's latest run used, then commit them. See [Recover scripts](/agent-evaluations/task-sets#recover-scripts).
  </Accordion>
  <Accordion title="The run warns that a task set isn't pinned">
    `eval.yaml` has no `version`, so the run used Laminar's latest version, and CI would pick up every new version as soon as it's pushed. Set `version` in `eval.yaml` to the version you want runs and CI to use. See [Pin task set versions](/agent-evaluations/task-sets#pin-task-set-versions).
  </Accordion>
</AccordionGroup>
