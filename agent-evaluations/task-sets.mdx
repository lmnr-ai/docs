A task set is a named, versioned group of [agent evaluation](/agent-evaluations/introduction) cases that Laminar stores for you. You define the cases once, then run the same version against every new version of your agent, so a score change means the agent changed rather than the test. Anyone on the project can add cases with `lmnr-cli eval push`, your repo pins the version it runs, and every run records exactly which version of the cases it used.

## Where task sets live

Each agent in your [evals folder](/agent-evaluations/evals-folder) has two parts, and they are kept in different places:

| | Agent scripts | Task sets |
| --- | --- | --- |
| What | `agent.yaml`, the Harbor agent class, Dockerfiles, start and seed scripts | The cases: `task.toml`, `instruction.md`, per-case data, verifier |
| Changes when | Your code changes | Someone adds or edits a case |
| Lives in | Your repo | Laminar, versioned |

Agent scripts depend on your code: a new database schema or a different start command changes them. Keeping them in the repo means they change in the same commit as the code, and your coding agent can update them alongside it. `lmnr-cli eval run` always uses the agent scripts in your repo: if `evals/<agent>/agent.yaml` is missing, the run fails with exit code `23` (`not_found`).

Task sets are data, so Laminar stores them, and anyone with access to the project can add cases without write access to your repo. Each change you push becomes a new version, and your repo pins the version each task set runs at.

Task set names are unique within a Laminar project. The agent's folder isn't part of the name, so two agents can't both have a task set called `smoke`: name them `support-smoke` and `billing-smoke` instead.

## Pin task set versions

Add a `task_sets` map to the agent's `agent.yaml`, with the version of each task set your runs and CI should use:

```yaml evals/support/agent.yaml
task_sets:
  billing: 7
  refunds: 2
```

Pins change only when you edit them, so a case someone adds in Laminar doesn't change what your CI runs until a commit bumps the pin. For each task set, a run uses the first of these that applies:

1. A version you name on the command line: `--task-set billing@8`, or `--task-set billing@latest` for the latest version.
2. Your local copy in `evals/<agent>/task_sets/<set>/`, as is, including edits you haven't pushed. If it's based on a different version than the pin, the run warns you.
3. The pinned version.
4. The latest version, only when you name the task set with `--task-set billing`.

A plain `lmnr-cli eval run support` runs the pinned task sets plus any local copies. Other task sets in the project run only when you name them with `--task-set`.

Local copies are working copies, not part of your repo. `lmnr-cli eval pull` and `lmnr-cli eval push` write an `evals/<agent>/.gitignore` that ignores `task_sets/`, so a CI checkout has no local copies and runs the pinned versions. Commit that `.gitignore`.

## Publish a task set

`lmnr-cli eval push` uploads your local copy and makes it the latest version:

```bash
lmnr-cli eval push support/billing    # one task set
lmnr-cli eval push support            # every local task set of the agent
```

Each push gets the next version number, which the command prints. `push` also writes `.lmnr.json` into the task set directory, which records the version your copy is now based on. Bump the pin in `agent.yaml` to that number when you want runs and CI to use it.

If someone else pushed the task set since your copy's version, `push` merges their version in first, task by task: tasks only they changed are taken, tasks only you changed are kept, and then your push goes through. A task that both of you changed stops the push with exit code `22` (`merge_conflict`) and changes nothing. Move your copy of that task aside, pull, and re-apply your edit.

## Fetch a task set

`lmnr-cli eval pull` brings Laminar's latest version into your evals folder:

```bash
lmnr-cli eval pull support/billing       # one task set
lmnr-cli eval pull support/billing@3     # a specific version
lmnr-cli eval pull support --all         # every task set agent.yaml pins
```

The pull merges with your local copy the same way a push does, so local edits you haven't pushed yet are kept. You don't need a local copy to run a task set: `lmnr-cli eval run` downloads the pinned version.

To see what Laminar has, run `lmnr-cli eval list`. It lists the project's task sets with their latest version.

## Recover agent scripts

Every evaluation keeps a copy of the agent scripts its run used. If your repo doesn't have them yet, for example because the [Laminar agent](/platform/laminar-agent) wrote them in its sandbox, fetch the ones the agent's latest run used and commit them:

```bash
lmnr-cli eval pull support
```

`--all` also fetches them when `evals/<agent>/` has no `agent.yaml`. If a script you have locally differs from Laminar's copy, the pull stops with exit code `22` (`merge_conflict`) and lists the files, without writing anything. Commit or move your changes aside first, or pass `--force` to overwrite them.

## Every run keeps the files it used

Each run's [evaluation](/evaluations/concepts) keeps the task files and the agent scripts it ran, so you can open them from the evaluation later. When the task files match a pushed version exactly, the evaluation also links to that task set version. A task set you haven't pushed yet, or a local copy with unpushed changes, runs without that link: the evaluation still shows its files, but no version is created. Only `push` creates versions, so a CI job on a pull request branch or a local experiment can't change the cases everyone else runs.

This makes runs repeatable. To compare a new version of your agent against an older run, run the same task set version:

```bash
lmnr-cli eval run support --task-set billing@7
```

Each run of a task set is charted in the evaluation group `<agent>/<task set>`, for example `support/billing`, so [comparing runs](/evaluations/comparing-runs) shows how your agent's score changed over time on the same cases.

## The Task sets page

The **Task sets** page in your Laminar project lists the project's task sets with their latest version. Open a task set to browse its tasks and their files, see each version and which tasks it added, removed, or changed, and find the evaluations that ran it.

On an evaluation, the **Task** tab shows each trial's task files and the **Scripts** tab shows the agent scripts the run used, with the git commit of your repo at the time. An evaluation that ran a pushed version links back to that task set version.
