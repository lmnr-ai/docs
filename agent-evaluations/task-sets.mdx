title: Task Sets - Version Agent Evaluation Cases in Laminar
sidebarTitle: Task sets

A task set is a named, versioned group of [agent evaluation](/agent-evaluations/introduction) cases that Laminar stores for you. You define the cases once, then run the same version against every new version of your agent, so a score change means the agent changed rather than the test. Anyone on the project can add cases with `lmnr-cli eval push`, your repo pins the version it runs, and every run keeps exactly the cases it used.

## Where task sets live

Each task set is one folder in your [evals folder](/agent-evaluations/evals-folder), `evals/<set>/`, with two parts kept in different places:

| | Scripts | Tasks |
| --- | --- | --- |
| What | `eval.yaml`, the Harbor agent class, Dockerfiles, start and seed scripts | The cases: `task.toml`, `instruction.md`, per-case data, verifier |
| Folder | `evals/<set>/` | `evals/<set>/tasks/` |
| Changes when | Your code changes | Someone adds or edits a case |
| Lives in | Your repo | Laminar, versioned |

Scripts depend on your code: a new database schema or a different start command changes them. Keeping them in the repo means they change in the same commit as the code, and your coding agent can update them alongside it. `lmnr-cli eval run` always uses the scripts in your repo: if `evals/<set>/eval.yaml` is missing, the run fails with exit code `23` (`not_found`).

Tasks are data, so Laminar stores them, and anyone with access to the project can add cases without write access to your repo. Each change you push becomes a new version, and your repo pins the version each task set runs at. Task set names are unique within a Laminar project.

Several task sets can share files, such as one agent class or Dockerfile, from a sibling folder without an `eval.yaml`, for example `evals/common/`. See [the evals folder](/agent-evaluations/evals-folder#share-files-between-task-sets).

## Pin task set versions

Set `version` in the task set's `eval.yaml` to the version your runs and CI should use:

```yaml evals/billing/eval.yaml
version: 7
```

Pins change only when you edit them, so a case someone adds in Laminar doesn't change what your CI runs until a commit bumps the pin. For each task set, a run uses the first of these that applies:

1. A version you name on the command line: `lmnr-cli eval run billing@8`, or `billing@latest` for the latest version.
2. Your local copy in `evals/<set>/tasks/`, as is, including edits you haven't pushed. If it's based on a different version than the pin, the run warns you.
3. The pinned version.
4. The latest version. The run warns you that the set isn't pinned, since CI would then pick up every new version.

Local copies are working copies, not part of your repo. `lmnr-cli eval pull` and `lmnr-cli eval push` write an `evals/<set>/.gitignore` that ignores `tasks/`, so a CI checkout has no local copies and runs the pinned versions. Commit that `.gitignore`.

## Publish a task set

`lmnr-cli eval push` uploads your local copy and makes it the latest version:

```bash
lmnr-cli eval push billing    # one task set
lmnr-cli eval push            # every task set with a local tasks/ folder
```

Each push gets the next version number, which the command prints. `push` also writes `tasks/.lmnr.json`, which records the version your copy is now based on. Set `version` in `eval.yaml` to that number when you want runs and CI to use it.

If someone else pushed the task set since your copy's version, `push` merges their version in first, task by task: tasks only they changed are taken, tasks only you changed are kept, and then your push goes through. A task that both of you changed stops the push with exit code `22` (`merge_conflict`) and changes nothing. Move your copy of that task aside, pull, and re-apply your edit.

## Fetch a task set

`lmnr-cli eval pull` brings Laminar's latest version into `evals/<set>/tasks/`:

```bash
lmnr-cli eval pull billing       # the latest version
lmnr-cli eval pull billing@3     # a specific version
```

The pull merges with your local copy the same way a push does, so local edits you haven't pushed yet are kept. You don't need a local copy to run a task set: `lmnr-cli eval run` downloads the pinned version.

To see what Laminar has, run `lmnr-cli eval list`. It lists the project's task sets with their latest version.

## Recover scripts

Every evaluation keeps a copy of the scripts its run used. When `evals/<set>/` has no `eval.yaml`, for example because the [Laminar agent](/platform/laminar-agent) wrote the scripts in its sandbox, `lmnr-cli eval pull <set>` first fetches the scripts the task set's latest run used, along with the shared files they reference. Commit them: runs only use the scripts in your repo.

If a script you have locally differs from Laminar's copy, the pull stops with exit code `22` (`merge_conflict`) and lists the files, without writing anything. Commit or move your changes aside first, or pass `--force` to overwrite them.

## Every run keeps the files it used

Each run's [evaluation](/evaluations/concepts) keeps the task files and the scripts it ran, so you can open them from the evaluation later. When the task files match a pushed version exactly, the evaluation also links to that task set version. A task set you haven't pushed yet, or a local copy with unpushed changes, runs without that link: the evaluation still shows its files, but no version is created. Only `push` creates versions, so a CI job on a pull request branch or a local experiment can't change the cases everyone else runs.

This makes runs repeatable. To compare a new version of your agent against an older run, run the same task set version:

```bash
lmnr-cli eval run billing@7
```

Each run of a task set is charted in the evaluation group named after it, for example `billing`, so [comparing runs](/evaluations/comparing-runs) shows how your agent's score changed over time on the same cases.

## The Task sets page

The **Task sets** page in your Laminar project lists the project's task sets with their latest version. Open a task set to browse its tasks and their files, see each version and which tasks it added, removed, or changed, and find the evaluations that ran it.

On an evaluation, the **Task** tab shows each trial's task files and the **Scripts** tab shows the scripts the run used, with the git commit of your repo at the time. An evaluation that ran a pushed version links back to that task set version.
