This page is the reference for the files `lmnr-cli eval run` reads. For a guided first dataset, start with the [quickstart](/agent-evaluations/quickstart).

`lmnr-cli eval run` treats every directory directly inside `evals/` that has a `harbor.yaml` as a dataset. A fuller layout, for an app with services and a database:

```
evals/
  README.md                       # how to run, how to add a case
  <dataset>/
    harbor.yaml                   # Harbor job config, plus the images tasks use
    agent/
      Dockerfile                  # services, app, scripts, baseline data
      agent.py                    # the Harbor agent
      start_stack.sh              # boot dependencies + the app, wait for readiness
      seed.*                      # load this case's data from /case
      run.*                       # drive the entry point, write result files
      verify.*                    # the verifier every case runs
      export_trajectory.*         # (optional) rebuild the trajectory if the app isn't instrumented
    tasks/
      dataset.toml                # the dataset's name and its pinned task versions
      <case>/
        task.toml
        instruction.md
        environment/
          case.json               # any format seed reads
        tests/
          test.sh                 # runs verify.*
          expected.json           # (optional) reference answer
```

Once you push the tasks to Laminar with [`lmnr-cli eval dataset push`](/agent-evaluations/eval-datasets), git keeps only `tasks/dataset.toml` and the task folders are git-ignored.

## harbor.yaml

A dataset's `harbor.yaml` is a Harbor job config (`agents`, `datasets`, `n_concurrent_trials`, and so on) with one extra key, `images`, that `lmnr-cli` reads. Relative paths resolve from the dataset folder, and the dataset folder is on `PYTHONPATH`, so `import_path: agent.agent:ClassName` points at `ClassName` in `<dataset>/agent/agent.py`.

```yaml evals/support/harbor.yaml
agents:
  - import_path: agent.agent:SupportAgent
    model_name: anthropic/claude-sonnet-5
datasets:
  - path: tasks
n_concurrent_trials: 4

images:
  myapp-evals:                  # referenced as docker_image = "myapp-evals"
    dockerfile: agent/Dockerfile
    context: ../..              # the repo root, so COPY can reach the app's source
  myapp-evals-browser:          # a second image, e.g. with a headless browser
    dockerfile: agent/browser/Dockerfile
    # no context: builds from agent/browser/
```

| Key | Required | What it does |
| --- | --- | --- |
| `images.<name>` | Yes | The image name tasks reference with `docker_image`. |
| `images.<name>.dockerfile` | Yes | Path to the Dockerfile, relative to the dataset folder. |
| `images.<name>.context` | No | Docker build context, relative to the dataset folder. Defaults to the Dockerfile's directory. |

Harbor ignores `images`, so `harbor run -c harbor.yaml` still works on its own once the images exist.

A run builds only the images its selected tasks reference. `lmnr-cli` rebuilds them on every run. When nothing changed, Docker reuses the cached build from earlier runs, so there are no tags to bump and no registry to push to. `images` is optional: without it, tasks pull `docker_image` from a registry or build their own `environment/Dockerfile`.

Two things matter when you write the Dockerfile:

- **Build from your live source**, so the evals exercise your production code.
- **`COPY` the specific paths you need instead of `COPY . .`.** A broad copy from the repo root would bake every task's `tests/` folder, including the reference answers, into the image where the agent can read them. From `evals/`, copy only the scripts in `agent/`.

It also helps to order layers from rarely to often changing (system packages, dependencies, scripts, app code), so an app change rebuilds one small layer. `.dockerignore` applies, and builds started by `lmnr-cli` never receive `.git` or `.env*` files.

## dataset.toml

`tasks/dataset.toml` is [Harbor's dataset manifest](https://www.harborframework.com/docs/datasets). `[dataset] name` is the dataset's name in Laminar, in Harbor's `org/name` form. `lmnr-cli eval dataset push` adds a `[[tasks]]` entry for each task, which pins the version of the task the dataset uses:

```toml evals/support/tasks/dataset.toml
[dataset]
name = "myapp/support"

[[tasks]]
name = "myapp/duplicate-charge"
digest = "sha256:..."
```

The dataset name is also the default evaluation group for its runs. Without a `dataset.toml`, the dataset is named after its folder. See [Eval datasets](/agent-evaluations/eval-datasets) for how pins are pushed, pulled, and merged.

## task.toml

Give each task its own `[task] name`, in the same `org/name` form. Eval datasets know a task by this name, not by its folder.

Set `docker_image` to an image name from `harbor.yaml` and leave the Dockerfile out of `environment/`. Every trial then starts from the same built image, and Harbor uploads the contents of `environment/` into `workdir` after the container starts. That is how `case.json` reaches a shared image.

```toml task.toml
[task]
name = "myapp/duplicate-charge"

[environment]
docker_image = "myapp-evals"
workdir = "/case"          # where environment/ is uploaded; defaults to the image's WORKDIR
cpus = 2
memory_mb = 4096

[agent]
timeout_sec = 600
```

A full stack per case is heavy, so set `cpus` and `memory_mb`. Locally all trials share your machine, so keep `n_concurrent_trials` low. Remotely, each trial gets its own sandbox, so you can raise concurrency for that run with `--n-concurrent`.

An image name that isn't in `harbor.yaml` is pulled from its registry, so public images work as-is.

### A Dockerfile for one task

This is a rare case: most datasets never need it. If one case needs a different system setup, put a Dockerfile in that task's `environment/` folder and remove `docker_image` from its `task.toml` (while `docker_image` is set, Harbor ignores the Dockerfile). The `environment/` folder then becomes the build context, and nothing is uploaded when the container starts. So the Dockerfile has to `COPY` the case data itself. It also has to start `FROM` a public base image, because the images from `harbor.yaml` aren't available to it.

## Secrets and env vars

Write every secret and setting as a `${VAR}` placeholder, and `lmnr-cli` fills them in when the run starts. Where you put the placeholder decides who receives the value:

```yaml evals/support/harbor.yaml
agents:
  - import_path: agent.agent:SupportAgent
    env:
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}   # the agent and the app it starts
      LOG_LEVEL: ${LOG_LEVEL:-info}             # optional, with a default
```

```toml task.toml
[verifier.env]
ANTHROPIC_API_KEY = "${ANTHROPIC_API_KEY}"      # the verifier, e.g. for an LLM judge

[environment.env]
TZ = "UTC"                                      # the container itself
```

Values come from your shell first, then from `.env.local` and `.env` in the current directory. With `--remote` they travel with the run as environment variables, and files that contain secrets are never uploaded. Commit a `.env.example` that lists the names, so teammates know what to fill in.
