Every trial runs two pieces of your code: a Harbor agent that starts the stack and drives your app's entry point, and a verifier that grades what the app produced. Both sit on top of the [production harness](/agent-evaluations/production-harness). The [quickstart](/agent-evaluations/quickstart) has a complete working example of each.

<Warning>
The agent can read everything in a task's `environment/` folder. Keep reference answers in `tests/`, which Harbor only uploads when the verifier runs. An answer placed in `environment/` can end up in the agent's context, making the evaluation useless.
</Warning>

## The Harbor agent

Subclass Harbor's `BaseInstalledAgent`, so the agent's commands run inside the container next to your app. `lmnr-cli` pins Harbor 0.25.0, and Harbor's [custom agents](https://docs.harborframework.com/agents/custom-agents) guide documents the full interface.

- **`install()` can stay empty** when everything is in the image. It runs in every trial, so anything it would install belongs in the image instead.
- **`run()` should stay thin.** Start the stack, seed the data, and call the driver. Run commands with `exec_as_agent`. The `agents[].env` values from `harbor.yaml` already reach every command, so use `env=` only for per-command extras.
- **Read the model from `self.model_name`**, so `--model` works.
- **Only import `harbor`, the standard library, and modules in the suite directory.** The class runs in the Harbor process, on your machine or in Laminar's orchestrator, and not inside the container.

## The driver

The driver is the script the agent runs inside the container. It triggers your entry point and waits for the result. For a synchronous entry point, such as an HTTP call or a function that returns, call it with a timeout and record the response. For an asynchronous one, such as a job on a queue, poll the status the app writes until it reaches a final state, up to a hard timeout.

Turn the result into an outcome the verifier can grade, and write the details to `/logs/agent/result.json`. Use `failed` and `timeout` as their own outcomes, so a crash is never mistaken for a wrong answer from the model:

```python
try:
    result = {"outcome": "completed", "reply": handle_ticket(case["ticket"])}
except TimeoutError:
    result = {"outcome": "timeout"}
except Exception as e:
    result = {"outcome": "failed", "error": repr(e)}
```

The driver should exit with `0` whenever it produced an outcome, including `failed` and `timeout`. A non-zero exit marks the trial as an error, which should mean the harness itself broke. Keep the driver's timeout shorter than the exec `timeout_sec`, and both shorter than the task's `[agent] timeout_sec`.

## The verifier

`tests/test.sh` is the entry point, and it can call anything: a Python script that compares against `expected.json`, a rubric, or an LLM judge with its key in `[verifier.env]`. It writes the reward to `/logs/verifier/reward.txt`, or to `/logs/verifier/reward.json` to report several named rewards, which become separate scores in Laminar. A pass or fail check is the easiest place to start, and an LLM judge works well for things like the tone or completeness of a reply. Where possible, pair the judge with a hard check on the state the agent changed.

Where the verifier runs is set by `environment_mode` under `[verifier]` in `task.toml`:

- **`"shared"`** (the default) runs in the agent's container after the agent finishes, and can read anything the run left behind, such as `/logs/agent/result.json` or the database.
- **`"separate"`** runs in a fresh container that only sees what the task declares: files listed in the top-level `artifacts = [...]`, plus snapshots taken by `[[verifier.collect]]` commands before the environment is torn down. Use it when the verifier needs its own dependencies, or when it shouldn't be able to see the app's internals.
