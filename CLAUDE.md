# Laminar Docs: Agent Notes

This is a Mintlify site. Pages are `.mdx`, navigation lives in `docs.json`, reusable fragments in `/snippets`, images in `/images`.

## Frontmatter

- **`description:` is REQUIRED on the 27 integration detail pages under `integrations/*` and optional elsewhere (reversed in LAM-2266 at the user's request).** The top-level `integrations.mdx` landing page is the deliberate exception and keeps title-only frontmatter. The earlier rule here said to omit descriptions everywhere; that was wrong on the SEO half. Verified against `mintlify dev`: the value becomes a real `<meta name="description">` plus `og:description` / `twitter:description`, which is the search snippet. It ALSO renders as a subtitle line between the H1 and the first section, so write it as a lead-in sentence that does NOT repeat the page's opening paragraph verbatim, or the top of the page reads twice. **Quote the whole value** (`description: "..."`) since these sentences usually contain a colon.
- Keep other pages' frontmatter to `title:` (and `sidebarTitle:` where needed) unless you're deliberately writing a snippet-worthy description.
- **An unquoted colon in `title:` is a YAML syntax error that fails the page build** ("syntax error in your frontmatter on line 0"). `title: Manual Evaluation API: Python, TypeScript, and HTTP` breaks; use "for" / a dash instead, or quote the whole value. `npx mintlify broken-links` does NOT catch this — only `npx mintlify dev` (watch its `! errors` block) or a real build does. Always load a page you've edited in `mintlify dev` before shipping.

## SEO

- The first ~150 words of a page matter disproportionately for search ranking and snippets. On integration and overview pages, lead paragraph one with what Laminar is plus the framework/SDK name (e.g. "Laminar is an open-source, OpenTelemetry-native observability platform for \<X\>. Trace, debug, and monitor ..."). Include the key product nouns (observability, OpenTelemetry, self-host/Helm, managed cloud) and action verbs (trace, debug, monitor).
- Defer "what the third-party SDK is" to paragraph two. The opening shouldn't burn SEO real estate on content that never names Laminar.

## Navigation and linking

- Every new page MUST be added to `docs.json`. Pages not listed there are unreachable from the sidebar even if they exist on disk.
- When deleting or moving a page, also `grep -r "integrations/<slug>"` across the repo to find inbound links. Common offenders: sibling integration pages often cross-link via a `<Note>` block and those must be updated in lockstep.
- Internal links use absolute paths from the docs root with no `.mdx` extension: `[Signals](/signals/introduction)`.
- Mintlify auto-redirects `/<group-slug>` to the first page in the group when you add a sidebar group whose slug matches an existing single-page URL (verified: `/signals` → 307 → `/signals/introduction` after converting `signals.mdx` into a `signals/` group). No explicit redirect entry is needed in `docs.json` when splitting a page into a group, but inbound links should still be updated to the canonical first-page URL.
- **The API Reference tab is generated from `openapi/openapi.yaml`** (`{"tab": "API Reference", "openapi": ...}` in `docs.json`, added by #218) and its pages have NO `.mdx` files. Deep-link them as `/api-reference/<tag-slug>/<kebab-cased operation summary>`, e.g. tag `LLM profiles` + summary `Create an LLM profile` → `/api-reference/llm-profiles/create-an-llm-profile`. `/api-reference` itself 307s to the first endpoint of the first tag. Verify any such link with a `curl -o /dev/null -w '%{http_code}'` against `mintlify dev`: `broken-links` reports these as fine whether or not they resolve, since it only checks `.mdx` targets.
- **Diff the spec against source before pointing a page at the generated reference.** `openapi.yaml` is hand-maintained, so it drifts exactly like the SDK docstrings do (it shipped with the same two stale LLM-profile claims the published packages had: "available only on self-hosted deployments, Laminar Cloud returns 404" on all five operations, and 8 of the 11 `provider` wire names). Both were corrected in the LAM-2247 PR; the Signals-side `llmProfileId` / `model` self-hosted notes are accurate and stay.
- Run `npx mintlify broken-links` from `/repos/docs` after any restructuring that moves or renames pages; it catches intra-docs link regressions in seconds and is more reliable than grepping for old paths.
- `npx mintlify broken-links` parses every `.md`/`.mdx` under the cwd, including this `CLAUDE.md`. A parse error here aborts the run before any broken-link output is printed. If the check dies on `CLAUDE.md`, temporarily `mv CLAUDE.md .CLAUDE.md.bak`, rerun, then restore. Long-term fix: escape stray `<tag>`-looking tokens in this file.

## Debugger (`/debugger/*`)

- The Debugger is its own top-level sidebar group (LAM-1733), not a single page under Platform. Pages (nav order): `debugger/introduction` (what/why, iteration-loop + coding-agent oriented), `debugger/setup` (install CLI → `lmnr-cli setup` → ask coding agent to instrument + run), `debugger/process` (record/inspect/replay loop the coding agent runs; renamed from `debugger/workflow`, sidebarTitle "The debugger process"), `debugger/caching` (backend cache mechanics, now LAST in nav). Canonical landing page is `/debugger/introduction`. The old `/platform/debugger` URL is gone; inbound links live in `platform.mdx` and `platform/cli.mdx`.
- The revamped debugger (LAM-1711 / `feat/debugger-rework-fe`) is **env-var driven**, not CLI-driven. Users run their agent with `LMNR_DEBUG=true` and iterate with `LMNR_DEBUG_REPLAY_TRACE_ID` + `LMNR_DEBUG_CACHE_UNTIL`. The old `lmnr-cli dev` interactive session model is fully REMOVED (no `dev` command, no `rollout_entrypoint` / `rolloutEntrypoint` observe flag — both dropped from the SDKs; scrubbed from `sdk/observe.mdx` and `guides/browser-use-debugger.mdx`).
- **Session continuation is default-on** (LAM-1750 / `refactor/debugger-followup` across `lmnr`, `lmnr-ts`, `lmnr-python`). The first `LMNR_DEBUG=true` run writes `.lmnr/debug-session.json` (renamed from `.lmnr/last-run.json`); every later run in the same directory OR any subdirectory (nearest-ancestor walk-up, same rule as `.lmnr/project.json`) reads it and rejoins the same session silently (no browser reopen), so `LMNR_DEBUG_SESSION_ID` is now OPTIONAL. The old `LMNR_DEBUG_FROM_LAST_RUN` / `LMNR_DEBUG_WRITE_LAST_RUN_TO_FILE` env gates are DELETED — don't document them. **Continuation ≠ replay**: rejoining records a fresh run; replay is still armed explicitly via `LMNR_DEBUG_REPLAY_TRACE_ID` + `LMNR_DEBUG_CACHE_UNTIL`. The `LMNR_DEBUG_RUN` pointer JSON: `session_id` FIRST, `trace_id` nullable, `cache_until` `string | null`. CLI: `lmnr-cli debug session new` mints a clean session + resets the file (bare session id to stdout; `--json` → `{sessionId,projectId,debuggerUrl}`; `--no-browser`); `debug session open` opens the session page (local-only, no network; `--json` → `{sessionId,debuggerUrl}`). **All `debug session` commands default their target to `.lmnr/debug-session.json`**; explicit ids are ALWAYS `--session-id` flags, never positionals. Session name is editable inline in the session-view header in addition to `debug session set-name`.
- **Sessions are block timelines** (LAM-1886 / lmnr #2003, lmnr-ts #267, lmnr-python #308). A debugger session is an ordered list of blocks in Postgres `debugger_session_blocks`: `trace` (written at ingest for any DEFAULT-type trace whose metadata carries `rollout.session_id`), `evaluation` (written at eval creation from the same metadata key), and `text` (standalone notes). Consequences for docs:
  - **Evals join the session automatically**: running any Laminar evaluation with `LMNR_DEBUG=true` makes the SDK stamp `rollout.session_id` into the eval's init metadata (`withSessionMetadata` / `_with_debugger_session_metadata`), resolved from env → `.lmnr/debug-session.json` → minted, exactly like traces. There is NO `lmnr-cli eval` command and no eval-specific env var. The UI renders each eval as a card with per-score averages plus a delta vs the previous eval in the session (green/red; brand-tint for a brand-new score name). Documented in `debugger/process.mdx` step 5 ("Prove the fix with an eval").
  - **`lmnr-cli trace` is GONE.** `trace append-note` was replaced by `lmnr-cli debug session add-note "<md>"`, which posts a standalone `text` block keyed by session id only (no trace/eval targeting, no `--trace-id` anywhere). The `LMNR_DEBUG_RUN_NOTES` / `LMNR_DEBUG_RUN_NOTES_FILE` env vars and the `rollout.note` metadata key are DELETED from both SDKs — never document any of them. `<span id='…' name='…' />` XML tags in notes still render as clickable chips (resolved session-wide, not per-trace).
  - `debug session summary` prints ALL blocks oldest-first: `<trace id="…"/>` and `<evaluation id="…"/>` self-closing tags plus raw note markdown (`--json` → array of `{id,createdAt,type,content}`). The old "note + `<trace end-time>`" per-trace format is dead.
- The backend table was renamed `rollout_sessions` → `debugger_sessions`. The UI route is `/project/<id>/debugger-sessions/<sessionId>`. Don't document the old `/rollout-sessions` path. (The metadata key and API paths still say `rollout` — `rollout.session_id`, `/v1/cli/rollouts/...` — that's expected, only surface the metadata key in SQL examples.)
- **"Long-Running" was dropped from debugger positioning** (LAM-1910): don't title or describe the debugger as "for long-running agents"; it's record/replay + evals for any agent. `debugger/introduction.mdx` title is now "AI Agent Debugger: Record, Replay, Evaluate".
- **Caching model** (LAM-1733): cache is served from the Laminar backend, keyed by `(trace_id, span_input_hash)`. Supported SDK integrations hash span input in cache mode, ask the backend before a live call, serve on hit, and flip to live mode on the first miss within a trace. The input hash **excludes system messages** (so iterating on the system prompt doesn't bust the cache). Caching integrations: OpenAI, Anthropic, Google GenAI, LiteLLM (Python-only); AI SDK is the only TS caching integration (covers all AI SDK providers). The debugger itself runs with all integrations + manual instrumentation — only caching is limited to that list. AI SDK additionally needs `wrapLanguageModel` per model call for caching to engage.
- **End-to-end walkthrough lives at `guides/debugger-end-to-end.mdx`** (LAM-1910 follow-up), a Python changelog-agent with a planted missing-f-string bug taken through record → notes → SQL span lookup → fix → replay (`CACHED` spans) → eval → `session summary`. All outputs on that page are real, captured against the local prod stack; the demo scripts are `/sandbox/scratch/agent.py` + `changelog_eval.py`. If the loop's surface changes (env vars, CLI verbs, summary format), this guide has verbatim outputs that must be re-captured, not hand-edited. Screenshots: `/images/guides/debugger-e2e-session.png` + `debugger-e2e-session-eval.png` (session `e8fb0cf5-…` in the sandbox project).
- **Reproducing the debugger loop against the local stack** (for re-capturing guide outputs): CLI login needs the `device_codes` table — staging Postgres may lag upstream migrations (0091 was missing; apply the committed migration SQL, don't hand-write DDL). App-server must be started with `NEXT_INTERNAL_URL=http://localhost:3000` or CLI-auth JWT verification fetches JWKS from laminar.sh and every `/v1/cli/*` call 401s. Approve the device code in the browser as `agent@lmnr.ai` at `/device?code=<user_code>`. Python SDK has no `LMNR_HTTP_PORT` env — pass `Laminar.initialize(http_port=8000, grpc_port=8001)` and `evaluate(..., http_port=8000, grpc_port=8001, frontend_port=3000)`; the SDK's printed `debugger_url` defaults to port 5667, which is cosmetic (session registration still hits 8000).

## CLI: two distinct tools, don't conflate

- `platform/cli.mdx` documents the **standalone `lmnr-cli`** npm package. `datasets/cli.mdx` documents a **different** CLI: `lmnr datasets`, bundled with the `@lmnr-ai/lmnr` SDK. They are not the same binary; a change to `lmnr-cli` (the standalone) does NOT necessarily touch the SDK-bundled `lmnr datasets`. Scope CLI doc edits to the right page.
- `lmnr-cli` auth model (lmnr-ts PR #243 / `feat/cli-better-auth`, paired with lmnr PR #1882): **user-token only.** EVERY project command (`sql` / `dataset` / `project` / `debug`) runs as the signed-in user (OAuth device flow via `lmnr-cli login`, BetterAuth JWT, routes to `/v1/cli/*`) — all wired through `withProjectClient` / `withUserToken` in `src/index.ts`. The CLI does NOT use a project API key at all (the `--project-api-key` path was fully dropped from `trace`/`debug` in commit 5ca9df66). The `LMNR_PROJECT_API_KEY` that `setup` mints into `./.env` is for the **app's SDK ingestion**, never the CLI itself. Earlier drafts of this PR had a dual-auth split (debug/trace on project key); that is dead — re-verify against `src/index.ts` before documenting, the model churned mid-PR.
- Projects are **directory-scoped**: `lmnr-cli setup` writes `.lmnr/project.json`; commands resolve the project as `--project-id` > nearest `.lmnr/project.json` (walk-up). There is no env-var way to pick the project (`resolveAuth` reads only the flag and the link file; verified by `src/auth/resolve.test.ts`). (User-facing docs avoid the Vercel/Supabase comparison per Robert's edit.)
- **Self-host config autoload** (lmnr-ts commit 46961f10; `AUTOLOADED_ENV_KEYS` in `src/utils/env-file.ts`): the CLI hydrates `LMNR_BASE_URL` / `LMNR_HTTP_PORT` / `LMNR_FRONTEND_URL` (NOT `LMNR_GRPC_PORT`, NOT `LMNR_LOG_LEVEL`, NOT `LMNR_PROJECT_ID`) from `.env` / `.env.local` in the cwd at startup, without overriding a real exported var. Reason: runners like Claude Code don't inject `.env` into the subprocess env. `base_url` carries no port by convention; the port comes from `LMNR_HTTP_PORT` or `--port`.
- **URL flags (changed; verify against `src/index.ts`)**: `login` takes ONLY `--frontend-url` (the auth issuer, default `https://www.laminar.sh`, env `LMNR_FRONTEND_URL`) and `--no-browser`. The old `login --base-url` / `--dashboard-url` flags and `LMNR_DASHBOARD_URL` env are GONE (dropped commit 1c9da6e). Data commands (`sql` / `dataset` / `project` / `debug`) resolve their API endpoint themselves via `--base-url` (env `LMNR_BASE_URL`, default `https://api.lmnr.ai`) + `--port` (env `LMNR_HTTP_PORT`). `setup` accepts both `--frontend-url` and `--base-url`.
- **`setup` re-run is NOT "always mint a fresh key"** (changed). It probes any already-configured key (process.env → .env.local → .env): if valid AND for the linked project, it leaves it untouched (no mint, no write); if valid but for a DIFFERENT project, it aborts (exit `key_mismatch`); only mints when no key is set or the existing one is invalid/revoked. Don't write "re-running mints a fresh key".
- **`setup` env-write target**: rewrites the key in place if it already lives in a file, else prefers an existing `.env.local` (never creates one — Python loaders ignore `.env.local`), else `.env`. Docs say "an existing `.env.local` if you have one, otherwise `.env`".
- The **`lmnr-cli` README on the branch is stale** (still lists removed `list` / `switch` / `dev` commands and a `profiles` credentials model). `src/index.ts` is the source of truth for the command surface; verify against it, not the README. Removed: `list`, `switch`, `dev`, the `profiles`/`active` credentials map. Added: `setup`, `project list`, flat single-user `credentials.json`.
- **`lmnr-cli@0.5.1` command groups** (the surface `platform/cli.mdx` enumerates in its two parentheticals, keep both in sync): `sql`, `dataset`, `signal`, `llm-profile`, `project`, `debug`, plus `setup` / `login` / `logout` / `ask` / `plugin`. What 0.5.1 added on top of 0.5.0: the whole `llm-profile` group (see the LLM profiles section), `signal versions <signal>`, `--llm-profile-id` + `--model` on `signal create` / `signal update`, and `dataset get <id>` / `dataset update <id> -n <name>` / `dataset delete <id>`.
- **`signal` command output cannot be captured live in this sandbox as of 2026-09-15.** Staging Postgres has `signals.current_version` and a `signal_versions` table but NOT the `signals.version` column that `frontend/lib/db/migrations/0109_lam_2211_signal_versions.sql` adds, so every `signal list` / `get` / `versions` call 500s with `column "version" does not exist`. Applying that migration would alter the persistent staging schema, which the sandbox rules forbid without an explicit ask — so the `signal versions` output block and the `version` / `llmProfileId` / `llmProfileName` / `model` fields on `signals/cli.mdx` are derived from `app-server/src/signals/service.rs` (`SignalResponse`, `SignalVersionResponse`) and the CLI's own `printSignal` / `printVersion` in `packages/lmnr-cli/src/commands/signal/index.ts`, not from a real run. ## Signals CLI (`/signals/cli.mdx`)

- Page lives under the **Signals** sidebar group (between `quickstart` and `clusters`), NOT under Platform, with a short "Manage Signals" pointer section in `platform/cli.mdx`. Same split as `datasets/cli.mdx` vs `platform/cli.mdx`.
- **The lmnr-ts #295 PR description does NOT match what shipped** — it advertises a `--filter "status = error"` DSL, `--trigger none`, and `lmnr-cli` 0.5.0. The merged code keeps `--filter` as `{column,operator,value}` **JSON** (deliberately, so new operators/value types need no CLI release), has NO `none` trigger kind, and shipped as **0.4.4**. Verify against `packages/lmnr-cli/src/commands/signal/validate.ts` + `src/index.ts`, never the PR body.
- **Three independent concepts, and the docs must keep them separate**: `--trigger` = WHEN it's evaluated (a *kind*: `root-span-finished` default, or `span-name` with repeatable `--span-name`), `--filter` = WHETHER it runs (property of the whole trace, repeatable, ANDed), `--mode` = HOW it's processed (`realtime` default / `batch`). **There is always exactly one trigger and no "no trigger" state** (`Trigger::RootSpanFinished` is `#[default]`, `signals/service.rs`).
- `--span-name` (trigger, matches the firing span batch) vs the `span_names` **filter** (plural, matches anywhere in the trace) are different things and are the easiest pair to conflate — every doc mentioning either needs the distinction called out.
- Filter columns are exactly `total_token_count` / `status` / `span_names`; source of truth is `FILTER_COLUMNS` in `app-server/src/signals/service.rs`. Create with no `--filter` seeds one default filter, `total_token_count > 1000`.
- **Mode wording comes from the UI, not the mechanism**: the drawer's helper text (`components/signals/create-signal-drawer/triggers-section/processing-mode-select.tsx`) says batch → "Results available within several hours", realtime → "Results in minutes, but each run is billed as 2 signal runs". Use those user-facing terms; the queue/provider-batch-API mechanism is enterprise internals. Note the UI's *default* mode is batch when `Feature.BATCH_SIGNALS` is on (always false in OSS), while the CLI/API default is always `realtime` — so "realtime is the default" is true for the CLI only.
- **Verifying `signal` commands end-to-end in this sandbox works and is worth doing** (every output on the page is real). Needs: app-server with `NEXT_INTERNAL_URL=http://localhost:3000` (else `/v1/cli/*` 401s on JWKS fetch), a prod frontend on 3000, `lmnr-cli login --frontend-url http://localhost:3000 --no-browser`, then approve at `/device?user_code=<code>` as `agent@lmnr.ai` — the approve step includes a **project picker** that must be submitted before the CLI unblocks. Point the CLI at the stack with a cwd `.env` holding `LMNR_BASE_URL=http://localhost` + `LMNR_HTTP_PORT=8000` and a hand-written `.lmnr/project.json`.
- Table output (`signal list`) is width-truncated from `process.stdout.columns`, so a piped run produces ellipsized columns. Capture it through a pty (`script -q -c "stty cols 170; <cmd>" /dev/null`) or the docs will show `root-span…`. Also `logger` writes to **stderr** with a timestamp/pid prefix that must be stripped for docs, while `--json` goes to stdout.
- `fields:` in `signal get` output is rendered from `Object.keys(structuredOutput.properties)`, whose order comes back from Postgres JSONB and is **not** the order you passed `--schema` in. Don't hand-write that line.

## Laminar Agent (`/platform/laminar-agent.mdx`)

- The agent is one core implementation (lmnr-private `app-server/src/agent/`) exposed on FOUR `AgentSource` surfaces: `Ui` (in-app chat-with-trace), `Mcp`, `Cli`, `Slack`. Public docs cover the three programmatic surfaces (MCP / CLI / Slack); the in-app UI chat is documented separately as "chat with trace" on `/platform/viewing-traces#chat-with-trace`. ## Vercel AI SDK integration

- **Two distinct telemetry APIs by AI SDK major version; `vercel-ai-sdk.mdx` documents BOTH via `<Tabs>` (v7 tab first).**
  - **v7 (GA):** register once with `import { registerTelemetry } from 'ai'; registerTelemetry(new LaminarAiSdkTelemetry())` and EVERY `generate*`/`stream*` call is traced with no per-call config. `LaminarAiSdkTelemetry` (exported from `@lmnr-ai/lmnr`, source `packages/lmnr/.../aisdk/v7-integration/index.ts`) calls `Laminar.initialize()` internally, so no separate init is needed. Constructor opts (`LaminarAiSdkTelemetryOptions`): `laminarOptions` (= `Laminar.initialize()` props, ignored if already initialized), `recordInputs` (default true), `recordOutputs` (default true), `createStepSpan` (default false). Per-call control is the `telemetry` block: `telemetry: { isEnabled: false }` disables one call site; `telemetry: { functionId, metadata }` names/annotates a span. NOTE: the SDK source ALSO ships `aiSdkTelemetry()` / `registerAiSdkTelemetry()` helpers and accepts `experimental_telemetry: { integrations: [...] }`, but docs follow the user's GA-facing surface: `registerTelemetry` from `ai` + the `telemetry` block. Do NOT label v7 as canary/beta/pre-release.
  - **v5/v6:** opt-in per call via `experimental_telemetry: { isEnabled: true, tracer: getTracer() }`. Forgetting the tracer is the most common "no traces" failure.
- The debugger caching step (`wrapLanguageModel` around each model) is IDENTICAL across versions; only the telemetry wiring differs. `getTracer`, `wrapLanguageModel`, `Laminar.flush()`, and `Laminar.shutdown()` all still exist.
- `await Laminar.shutdown()` (or `Laminar.flush()`) is still required at the end of short-lived scripts/serverless to flush the last spans, on BOTH integration styles.
- Next.js: Laminar must go in `instrumentation.ts` with a `NEXT_RUNTIME === 'nodejs'` guard, and `@lmnr-ai/lmnr` must be in `serverExternalPackages` in `next.config.ts`. OpenTelemetry uses Node-specific APIs Next.js cannot bundle.
- Coexistence with `@vercel/otel`: do NOT call `Laminar.initialize()` (that registers a second provider). Pass `new LaminarSpanProcessor()` into `registerOTel({ spanProcessors: [...] })` instead.
- Direct SDK clients (OpenAI, Anthropic) imported outside `instrumentation.ts` are not auto-instrumented in Next.js. Call `Laminar.patch({ OpenAI, anthropic })` where the client is constructed.
- AI SDK is TypeScript-only; there is no Python AI SDK integration page to write.

## Span types in manual instrumentation

- Transcript view is driven by span **type**, not span name. It renders the user input, LLM turns, tool calls, and subagent cards; `DEFAULT` spans are filtered out and only visible in Tree view (see `frontend/components/traces/trace-view/transcript/index.tsx` and `store/utils.ts`). A manually-instrumented tool wrapped with `@observe()` shows up in Tree view but NOT in transcript view unless you pass `span_type="TOOL"` / `spanType: "TOOL"`. This is the single highest-leverage instrumentation change for agent traces.
- Dedicated page for this lives at `/tracing/structure/span-types`. Integration and guide pages that describe manual tool wrapping should link there instead of re-explaining the TOOL/DEFAULT distinction inline.
- Python SDK supports `Literal["DEFAULT", "LLM", "TOOL"]` on `@observe(span_type=...)` / `Laminar.start_as_current_span(span_type=...)` / `start_active_span` / `start_span`. TypeScript supports the full `SpanType` union (adds `EXECUTOR`, `EVALUATOR`, `HUMAN_EVALUATOR`, `EVALUATION`, `CACHED`) — user-facing docs keep the value sets aligned but should document only `DEFAULT` / `LLM` / `TOOL` as the types a human should reach for. The others are for the evaluations framework or internal auto-instrumentation.

A server-generated `points[].id` is NOT returned (the response is just the eval id), so callers who want to update later MUST mint the datapoint UUID client-side. `executorOutput` + `scores` are accepted here, so an HTTP backfill needs no update call at all.
  - **`index` is per-point and NOT auto-incremented server-side** — every point sent without one gets `0` (verified: a 3-point batch with no `index` produced three rows all at `index=0`; the CH order key is `(project_id, evaluation_id, id)`, nothing derives position). The 0,1,2,… numbering people expect comes from the SDK `evaluate()` loop passing its own counter (`evaluations.ts` `evaluateTask(datapoint, index)`, `evaluations.py` `evaluate_task(datapoint, index)`), NOT from the backend. This matters more than display order: the compare-runs view LEFT JOINs the two runs **`ON p.index = c.index`** (`frontend/lib/actions/evaluation/query-builder.ts`), so all-zero indices fan out into a cross join (verified: 3 rows x 3 rows = 9). Any doc describing `index` must say "not auto-incremented" and tie it to run comparison, not just row order.
  - **`groupName` is NOT inherited from the evaluation** on the datapoints endpoint — it defaults to `default` per request. Omitting it writes rows outside the eval's group, which silently drops them from the group progression chart (`getEvaluationTimeProgression` filters on `group_id`). This is the easiest way to get a broken-looking eval; the page carries a `<Warning>` about it.
  - `POST /v1/evals/{id}/datapoints/{dp_id}`: **`scores` is a REQUIRED field** (400 `missing field scores`) — the executor/scorer split sends `"scores": {}` first. Scores MERGE across calls (`jsonMergePatch`), and an omitted `executorOutput` preserves the stored value. Unknown datapoint id returns **500**, not 404.
  - `traceId` is caller-supplied (nothing links a datapoint to a trace implicitly; the SDKs just read the active span via `Laminar.getTraceId()` / `get_trace_id()`, and TS `createDatapoint` defaults a missing one to a random `newUUID()`). Omitted over raw HTTP it stores the NIL UUID and the row simply has no transcript — no error. The endpoint accepts BOTH the hyphenated UUID and the raw 32-hex OTel form (both normalize to the same stored UUID). **Keep this OUT of the page**: a draft spelled all of it out in an `### Attaching traces to datapoints` subsection and Robert cut it as too much detail — anyone wiring their own OTel already knows what a trace id is. One sentence pointing at `/tracing/otel` is the agreed depth. Recorded here only so the behavior doesn't have to be re-derived.
  - `uuidgen` is NOT installed in this sandbox; shell examples use `python3 -c 'import uuid; print(uuid.uuid4())'`. `jq` IS available.
- **Voice template for new evaluation pages**: follow `signals/introduction.mdx`. Open with a bold thesis sentence containing 2-3 inline links (e.g. `**[compares them](/evaluations/comparing-runs) across [runs](/evaluations/concepts) and [groups](...)**`). Use italics for rhetorical hypotheticals (`*is this version better*`). Put the primary `<Frame>` image right after the opener, not after multiple sections. ## Mastra integration

- `MastraExporter` is Mastra-specific and plugs into Mastra's own `Observability` config — it is NOT a standalone initializer like Vercel AI SDK's `getTracer()`. Shape: `new Observability({ default: { enabled: false }, configs: { <name>: { serviceName, exporters: [new MastraExporter()] } } })`. Minimum versions: `@lmnr-ai/lmnr >= 0.8.21`, `@mastra/core >= 1.0.0`, `@mastra/observability >= 1.0.0` — `@mastra/core@1.0.0` is the first stable with the `ObservabilityEntrypoint` field on `new Mastra({ observability })` and matching `Observability` class in `@mastra/observability@1.0.0`. Don't bump these to a higher floor unless a new API is actually needed.
- `default: { enabled: false }` is load-bearing. Omitting it double-emits spans via Mastra's built-in default exporters alongside Laminar. Always call it out in docs.
- Mastra's `Observability` has NO `.flush()` method — `await observability.shutdown()` IS the flush path. Document `observability.shutdown()` before `Laminar.shutdown()` on every end-of-script example.
- `MastraExporter({ linkToActiveContext: true })` is the default. When a Mastra agent runs inside an active OTel span (e.g. `observe()` or `@vercel/otel`), the exporter rewrites Mastra trace ids onto the caller's trace so `observe()` root + Mastra subtree render as one trace. Readers hitting "two separate traces" have overridden this to `false` or called `Laminar.initialize()` after `new Mastra(...)`.
- `MastraExporter({ realtime: true })` force-flushes on every span end; use for scripts/serverless. Leave default for long-running services.
- Mastra AI SDK v6 tool `execute` takes `(inputData)` whose fields are under `inputData.context` — NOT destructured at top level. `execute: ({ from, to }) => ...` silently receives `undefined`. Write `execute: (inputData) => { const { from, to } = inputData.context; ... }`.
- Mastra v1.28 removed `maxSteps`; use `stopWhen: ({ steps }) => (steps?.length ?? 0) >= N` (or the `stepCountIs` helper from the AI SDK equivalent). Older docs showing `maxSteps` are wrong.
- Multi-subagent demo shape: wrap each sub-agent in a `createTool({ execute: async (inputData) => { const res = await subAgent.generate(...); return {...}; } })`. Laminar nests the sub-agent's full run (its own turns and tool calls) under the parent tool span. Rich tree-view screenshots come from this pattern (concierge → bookFlight tool → flight-agent run → gpt-5-mini LLM → lookup_flights tool). Flat-single-agent demos look thin by comparison.
- When shipping both transcript- and tree-view screenshots (`/images/traces/<integration>.png` + `<integration>-tree.png`), verify each filename matches what the image actually shows before committing — the `Tree`/`Transcript` dropdown label in the top-left of the trace pane is the ground truth, and the right-hand Span Input/Output panel alone cannot tell the two views apart. Misfiled screenshots ship silently: the page builds, Mintlify renders, and only a reviewer comparing caption to pixels notices.

## Span batching (`/sdk/batching`)

- The byte-size flush trigger (LAM-2051) is **opt-in in both SDKs** and has a two-option surface: `flushBySize` / `flush_by_size` (default off) plus `maxExportBatchSizeBytes` / `max_export_batch_size_bytes` (default 32 MiB). Passing only the byte limit is a no-op — it must never be documented as enabling the feature on its own. `disableBatch` wins over both.
- **The two SDKs behave differently on the wire and docs must not claim a hard bound.** Verified with 12 spans of ~1 MiB against a 4 MiB limit: TS produced four exports of exactly 3 MiB (it flushes before enqueueing the triggering span), Python produced three exports, one of them ~6 MiB, because its flush is handed to a background thread and spans landing meanwhile ride along. "Approximate / leave headroom" is the honest framing.
- Defaults that differ and are easy to get wrong: `maxExportBatchSize` is **512 in TS but 64 in Python**; scheduled delay is 5000 ms in both (OTel default, neither SDK overrides it).
- Ingest limits are `HTTP_PAYLOAD_LIMIT` (5 MiB) and `GRPC_PAYLOAD_LIMIT` (25 MiB) in `lmnr/app-server/src/env/server.rs`. Both are **below** the SDK's 32 MiB default, so the self-hosting guidance on the page is load-bearing, not filler. Neither var is documented under `/self-hosting/*` yet.
- **An oversized export surfaces differently per transport, and troubleshooting pages must name both** so they are greppable: gRPC (the SDK default) gets tonic's `Status::out_of_range`, `Error, decoded message length too large: found <N> bytes, the limit is: <M> bytes` (`tonic/src/codec/decode.rs`); HTTP gets actix's 413 rewritten to `PAYLOAD_TOO_LARGE_MESSAGE` in `app-server/src/main.rs`. Robert's rule on `/tracing/troubleshooting`: put the literal status code and message in the heading and Problem section, never a paraphrase like "a payload-too-large error".
- **`disableBatch` blocks the app in Python but not in TypeScript.** Python's `SimpleSpanProcessor.on_end` calls `span_exporter.export()` on the calling thread; the JS one fires an unawaited promise. Both send one request per span, so "not a production setting" holds for both, but only say "blocks your application" about Python.
- **Verifying export sizes without the stack**: run the SDK against a throwaway `http.server` that logs request sizes, with `forceHttp` / `force_http=True` and `httpPort` pointed at it. Two traps: the JS OTLP exporter sends **chunked** (no `Content-Length`, so decode the chunk sizes or every request reads as 0 bytes), and the Python exporter **gzips** regardless of `OTEL_EXPORTER_OTLP_COMPRESSION`, so its numbers are compressed. Use incompressible payloads (`secrets.token_hex`) when the absolute size matters.
- `pip install lmnr==0.7.59` fails to resolve (it pins `opentelemetry-semantic-conventions==0.60b1`, which no `opentelemetry-instrumentation` release matches). Use `/repos/lmnr-python/.venv` instead; it tracks the repo version, which matched PyPI.

Only the *Signal* profile picker is gated, by `Feature::SignalLlmProfiles` / `Feature.SIGNAL_LLM_PROFILES` = `LAMINAR_CLOUD !== "true"`. So "self-hosted only" applies to Signals, never to profiles or the playground.
- **The CLI surface shipped in `lmnr-cli@0.5.1`** (with `@lmnr-ai/{lmnr,client,types}@0.8.46`): `llm-profile` / `llm-profiles` with `list | get | create | update | delete`, documented in `## Manage profiles from the CLI` on this page plus a pointer section in `platform/cli.mdx`. Group flags are `--project-id` / `--base-url` / `--port` / `--json`; credential flags are `--api-key`, `--access-key-id` + `--secret-access-key`, `--token`, `--region`, `--resource-id`, `--provider-base-url`, `--api-version`, repeatable `--header Name=Value`, repeatable `--model`. Auth type is inferred from which flags you pass. **`--provider-base-url` (the provider endpoint) vs `--base-url` (the Laminar API) is the trap** and the page carries a `<Warning>` about it.
- **Three claims in the published packages are stale; do NOT mirror them into docs** (verified against the app-server and by creating profiles over the CLI on Cloud-shaped routes): the `llm-profile` group help says "Manage the workspace LLM profiles signals can run on (self-hosted only)", `packages/client/src/resources/llm-profiles.ts` and `packages/lmnr-cli/CLAUDE.md` both say "Self-hosted only: on Laminar Cloud every route 404s", and `--provider` help + `LlmProfileProvider` in `packages/types/src/llm-profiles.ts` list only 8 of the 11 provider wire names (`anthropic`, `groq`, `mistral` missing; the CLI does no local validation, and all 11 were confirmed accepted by the server). Profiles themselves are not Cloud-gated (see the bullet above); only pinning a Signal to one is.
- **`## Manage profiles over the API` is deliberately thin.** It is one paragraph linking the five generated reference pages, the self-hosting base-URL `<Note>`, two provider-shaped request bodies (Bedrock `config`/`secrets` split, custom gateway `headerNames` + `secrets.headers`), and the PATCH rules. The method/path table, the plain create `curl` with its full response dump, and the `400`/`404`/`409` enumeration were removed once the API Reference tab covered them: don't re-add them. What stays inline is only what an OpenAPI schema cannot express, i.e. which `config`/`secrets` combination each provider needs and the update traps (a supplied `config` replaces the whole object, changing `provider` requires `config`, dropping a model a Signal runs on is a `409`).
- **Don't re-add "the selected model serves the whole run"** (Robert, LAM-2247 review: too much detail, confusing). The underlying fact holds (a profile-backed Signal ignores `LLM_PROVIDER` and the `LLM_MODEL_SMALL/MEDIUM/LARGE` tiers) but the `## Route Signals through a profile` bullet list is about what the user picks, not about tier resolution.
- **CLI update semantics to keep straight** (all server-side, all verified): `--model` REPLACES the whole model list, any config flag replaces the whole config object (so re-pass every config field the provider needs), an omitted secret keeps the stored value, an update with no flags is an error, and a delete is refused with 409 while a Signal uses the profile.
- `@lmnr-ai/client@0.8.46` also exposes `client.llmProfiles` (list/get/create/update/delete) and `client.signals` (list/get/listVersions/create/update/delete). **Neither is on `/sdk/client` yet** — that page is a per-method reference and adding them is its own task; the `signals` methods additionally can't be verified in this sandbox (see the CLI section's `signals.version` note).
- 11 provider wire names (`openai_completions`, `openai_responses`, `anthropic`, `gemini`, `groq`, `mistral`, `bedrock`, `azure_chat_completions`, `azure_responses`, `azure_anthropic`, `custom`) collapse in the UI into 8 providers plus an **API shape** sub-select for OpenAI (Chat Completions / Responses API) and Azure (Chat Completions / Responses API / Anthropic Messages). Label strings live in `frontend/components/workspace/llm-profiles/types.ts` (`OPENAI_SHAPE_OPTIONS` / `AZURE_SHAPE_OPTIONS`) — use those, not the enum values. `custom` speaks OpenAI Chat Completions only and appends `/chat/completions` to the base URL.
- Secrets are **write-only**: reads return `first3***last3` masks (fully starred when the value is ≤ 9 chars) plus custom header *names*; an omitted secret on update keeps the stored value (true for the UI and PATCH alike). Encryption is XChaCha20-Poly1305 with the profile id as AAD under `AEAD_SECRET_KEY`, written by the frontend and read by app-server, so a key mismatch surfaces as "cannot decrypt credentials" at run time.
- **Delete semantics differ by consumer and both belong in docs**: `playgrounds` has a composite FK `ON DELETE SET NULL` (deleting a profile or removing a model just clears the playground's selection), `signals` has `ON DELETE RESTRICT` plus a both-or-neither CHECK, so the delete is refused with a 409 while a Signal uses it.
- Empty-state strings to quote verbatim: playground shows **No LLM profiles configured** (`components/playground/providers-alert.tsx`), the Signal picker shows **No profiles yet** (`components/signals/create-signal-drawer/llm-profile-section.tsx`), and a legacy Signal (existing row with no profile) gets a banner telling you it still runs on `LLM_PROVIDER`. A workspace with exactly one profile preselects it plus its first model.
