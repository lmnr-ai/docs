title: Manage Signals from the CLI
---

The `lmnr-cli signal` command creates, updates, and deletes [Signals](/signals/introduction) from your terminal, so a Signal is a scriptable resource instead of a form you fill in. It ships in the standalone [`lmnr-cli`](/platform/cli) npm package, so you do not need the `@lmnr-ai/lmnr` SDK installed to use it.

A Signal created this way is identical to one created in the UI: same payload schema rules, same default trigger, and the same auto-created critical-severity alert. Anything you create from the CLI opens and edits normally in the Signals UI, and the reverse is also true.

<Tip>
Every command takes `--json` and writes structured output to stdout while human-readable messages go to stderr. That plus a comprehensive `--help` on each subcommand makes this the surface to hand an AI coding agent when you want it to define Signals for the failure it just debugged.
</Tip>

## Install

```bash
# Run directly with npx (no install)
npx lmnr-cli@latest signal list

# Or install globally
npm install -g lmnr-cli
```

The rest of this page assumes a global install (`lmnr-cli signal ...`). With `npx`, prefix each command with `npx lmnr-cli@latest`.

## Authenticate and link your project

The CLI authenticates as you, the signed-in user. Run `lmnr-cli setup` once in your project: it logs you in and links the current directory to a project by writing `.lmnr/project.json`. Every signal command then runs against that linked project.

```bash
lmnr-cli setup
```

Target a different project explicitly with `--project-id` on any command:

```bash
lmnr-cli signal list --project-id <your-project-id>
```

See [Authenticate](/platform/cli#authenticate) and [Directory-scoped projects](/platform/cli#directory-scoped-projects) for details.

## Referring to a Signal

`list` takes an optional name fragment to filter on (case-insensitive substring). `get`, `update`, and `delete` take a `<signal>` argument that accepts **either an id or a name**, so you can script against a stable name and never resolve an id first:

```bash
lmnr-cli signal get "Refund requests"
lmnr-cli signal get 29b937f1-7e3c-4768-a5e3-7e891c2d7d0a
```

<Note>
A name that matches more than one Signal is an error listing the candidates, not a silent pick. `update` and `delete` are destructive, so ambiguity is never resolved for you. Pass the id to disambiguate.
</Note>

## Create a Signal

`create` takes the name as a positional argument plus the two things every Signal needs: a `--prompt` describing what to detect, and a `--schema` naming the fields to extract.

```bash
lmnr-cli signal create "Refund requests" \
  --prompt "Detect when the user asks for a refund. Extract the reason." \
  --schema '{"properties":{"reason":{"type":"string","description":"Refund reason"}}}'
```

With no `--trigger`, the Signal is seeded with the same default trigger the UI uses: run when the root span finishes, on traces over 1000 tokens. So the command above produces a live Signal that starts evaluating new traces immediately.

### Payload schema

`--schema` is the JSON schema for the extracted payload. These are the fields that become filterable columns on `signal_events`, so keep them small and stable. The rules are identical to the UI's:

- Field names must be valid identifiers: `^[a-zA-Z_][a-zA-Z0-9_]*$`.
- Field types are `string`, `number`, or `boolean`. For a fixed set of values, use a `string` field with an `enum` array.
- Every field is required. `type` and `required` are filled in for you when omitted, so `{"properties":{...}}` is the whole schema you need to write.

```bash
lmnr-cli signal create "Agent failures" \
  --prompt "Find failures in this run. Rate the severity and name the tool at fault." \
  --schema '{"properties":{
    "severity":{"type":"string","enum":["low","high"],"description":"How bad it was"},
    "failed_tool":{"type":"string","description":"Tool that failed"},
    "recovered":{"type":"boolean","description":"Whether the agent worked around it"}
  }}'
```

### Sampling and initial state

```bash
# Evaluate only 25% of matching traces
lmnr-cli signal create "High volume check" --prompt "..." --schema '...' --sample-rate 25

# Create it paused, to configure triggers before it starts consuming traces
lmnr-cli signal create "Draft signal" --prompt "..." --schema '...' --disabled

# Create it with NO trigger at all (it never fires until you add one)
lmnr-cli signal create "Backfill only" --prompt "..." --schema '...' --no-default-trigger
```

`--sample-rate` takes a whole percent from 1 to 95. Omit it to evaluate every matching trace.

<Note>
Creating a Signal also creates a **Critical**-severity event alert subscribed to your email, exactly as the UI does (plus a new-cluster alert when clustering is enabled). Route it to Slack, change the severity, or add output-schema filters from the Signal's **Settings > Alerts** section. See [Alerts](/signals/alerts).
</Note>

## Triggers: conditions and filters

A trigger has two lists that do different jobs, and they are not interchangeable:

| List | Question it answers | Columns |
|------|--------------------|---------|
| `conditions` | **When** to evaluate, decided from a single batch of spans | `root_span_finished`, `span_name` |
| `filters` | **Whether** to run, based on the whole trace | `total_token_count`, `status`, `span_names` |

An empty `conditions` list never fires. An empty `filters` list passes, so the Signal runs on every trace that fires.

Pass each trigger as one JSON object to `--trigger`. The flag is repeatable, and every entry is `{"column": ..., "operator": ..., "value": ...}`:

```bash
lmnr-cli signal create "Agent failures" \
  --prompt "Find failures. Rate severity." \
  --schema '{"properties":{"sev":{"type":"string","enum":["low","high"],"description":"Severity"}}}' \
  --trigger '{
    "conditions":[{"column":"span_name","operator":"includes","value":["agent.run"]}],
    "filters":[{"column":"status","operator":"eq","value":"error"}]
  }'
```

That Signal evaluates a trace when a span named `agent.run` shows up, and then only runs if the trace errored.

### Column reference

| List | Column | Operators | Value |
|------|--------|-----------|-------|
| `conditions` | `root_span_finished` | `eq` | the string `"true"` |
| `conditions` | `span_name` | `eq`, `ne`, `includes` | a span name, or an array of names with `includes` |
| `filters` | `total_token_count` | `eq`, `ne`, `gt`, `gte`, `lt`, `lte` | a finite number |
| `filters` | `status` | `eq`, `ne` | `"error"` or `"success"` |
| `filters` | `span_names` | `eq` (includes), `ne` (does not include) | a span name |

<Warning>
`span_name` (a condition) and `span_names` (a filter) are different columns. The condition matches only the batch of spans that fired the trigger; the filter asks whether that name appears anywhere in the trace. Putting a column in the wrong list is rejected with an error naming the correct list, because a trigger that looks configured but silently never fires is the worst outcome.
</Warning>

## Update a Signal

`update` is a **partial patch**: only the flags you pass are changed, and everything you omit keeps its stored value. Changing a prompt cannot accidentally clear sampling or reactivate a paused Signal.

```bash
lmnr-cli signal update "Refund requests" --prompt "Detect refund asks only"
lmnr-cli signal update "Refund requests" --schema '{"properties":{"reason":{"type":"string","description":"Why"}}}'
lmnr-cli signal update "Refund requests" --sample-rate 10
lmnr-cli signal update "Refund requests" --no-sampling      # evaluate every matching trace
lmnr-cli signal update "Refund requests" --disabled         # pause
lmnr-cli signal update "Refund requests" --no-disabled      # resume
```

Pausing from the CLI is the same operation as flipping the **Active** switch in the UI: new traces stop being evaluated, backfills are rejected, and existing events and clusters are kept. See [Pause and resume a Signal](/signals/quickstart#pause-and-resume-a-signal).

`--trigger` on `update` **replaces the whole trigger set** rather than adding to it, since triggers have no stable client-facing identity. Pass every trigger you want the Signal to end up with:

```bash
lmnr-cli signal update "Refund requests" \
  --trigger '{
    "conditions":[{"column":"root_span_finished","operator":"eq","value":"true"}],
    "filters":[{"column":"total_token_count","operator":"gt","value":"5000"}]
  }'
```

An update with no flags is an error listing the valid ones, never a silent no-op.

## List and inspect

`list` prints one row per Signal with its status, sampling, and trigger count. `get` prints one Signal with its prompt, payload fields, and each trigger rendered in readable form.

```bash
lmnr-cli signal list
lmnr-cli signal list refund          # filter by name substring
lmnr-cli signal get "Refund requests"
```

Add `--json` to get the raw objects on stdout, which is what you want in a pipeline:

```bash
# Every paused signal's name
lmnr-cli signal list --json | jq -r '.[] | select(.disabled) | .name'

# The fields a signal extracts
lmnr-cli signal get "Refund requests" --json | jq '.structuredOutput.properties | keys'
```

## Delete a Signal

```bash
lmnr-cli signal delete "Refund requests"
```

<Warning>
Deletion is permanent. It also removes the Signal's triggers, its alerts, and every signal event it produced. A name must match exactly one Signal. If you only want to stop a Signal from running, use `--disabled` instead: that keeps its events and clusters queryable.
</Warning>

## Reference

```bash
lmnr-cli signal [command]
```

### General options

Shared by every `signal` subcommand.

```
  --project-id <id>   Target project id. Defaults to the linked .lmnr/project.json
  --base-url <url>    Base URL for the Laminar API. Defaults to https://api.lmnr.ai or LMNR_BASE_URL env variable
  --port <port>       Port for the Laminar API. Defaults to 443 or LMNR_HTTP_PORT env variable
  --json              Output structured JSON to stdout
```

### Commands

```
  list [name]                List signals in the project, optionally filtered by name substring
  get <signal>               Show one signal with its triggers
  create [options] <name>    Create a signal with a payload schema and triggers
  update [options] <signal>  Update a signal (only the flags you pass are changed)
  delete <signal>            Delete a signal, its triggers, its alerts, and its events
```

### create

```
Arguments:
  name                     Signal name (unique per project, max 255 chars)

Options:
  --prompt <prompt>        LLM instruction describing what to detect in a trace (required)
  --schema <json>          Payload schema as JSON (required)
  --trigger <json>         Trigger as JSON (repeatable). Omitted → the default trigger
  --no-default-trigger     With no --trigger, create the signal with NO trigger
  --sample-rate <percent>  Evaluate only this percent of matching traces (1-95)
  --disabled               Create the signal deactivated
```

### update

```
Arguments:
  signal                   Signal id or name

Options:
  --prompt <prompt>        Replace the LLM instruction
  --schema <json>          Replace the payload schema (same shape as create)
  --trigger <json>         Replace ALL triggers with these (repeatable)
  --sample-rate <percent>  Set the sampling percent (1-95)
  --no-sampling            Clear sampling (evaluate every matching trace)
  --disabled               Deactivate the signal
  --no-disabled            Reactivate the signal
```

Every command carries its own examples in `--help`, including the full trigger model:

```bash
lmnr-cli signal create --help
lmnr-cli signal update --help
```

### Self-hosting

Point the CLI at your instance with `--base-url` and `--port`, or set `LMNR_BASE_URL` and `LMNR_HTTP_PORT` once. See [Self-hosting](/platform/cli#self-hosting).

```bash
lmnr-cli signal list --base-url http://localhost --port 8000
```
