A tool times out, and the agent makes up the result. The final answer still looks complete. The trace holds the evidence, just as it does when a user asks the same question three times or an agent reports a task done without finishing it.

One trace can contain hundreds of spans and hundreds of thousands of tokens of prompts, tool output, and retries. People are bad at reading that much context. You skim, trust the agent's own summary, and stop at the first explanation that fits. Finding the failure in one trace is hard. At ten thousand runs a day, nobody reviews them by hand.

**A Signal does that reading for you.** You describe what to look for in plain language and name the fields you want back. On each matching trace, an agent searches across spans and opens the relevant ones. When it finds what you described, it records a structured event with references to the evidence. You **[query](/platform/sql-editor), [cluster](/signals/clusters), and [alert](/signals/alerts) on** those events.

The agent runs on **[flow-1](#signals-run-on-flow-1-our-model-for-reading-traces)**, a model we trained to read traces. It matches GPT-6-sol on failure detection at 23x lower cost, about a tenth of a cent per trace. That cost lets you run Signals on all production traces instead of a sample.

## Signals read the whole trace, not the final answer

**A Signal reads every LLM turn, tool call, subagent, retry, and error, from the first span to the last.** Grading only your agent's last LLM output misses that context.

Most failures in a long agent run are invisible from the output alone:

- A tool returned an error in step 12 and the agent worked around it. The final answer still sounds confident and complete.
- The agent issued the same search three times with the same arguments. The answer is right but cost three times what it should have.
- A subagent returned nothing usable, and the parent filled the gap with a plausible substitute.
- The agent broke a rule from its system prompt forty steps ago. The only evidence is a subtly wrong deliverable.

By the time the agent writes its final message, the evidence is dozens of spans earlier. Scoring the last LLM span can't account for it. A Signal can identify *which tool failed, what the agent did about it, and what the user ended up believing*, even when *the answer looks fine*.

## Signals run on flow-1, our model for reading traces

Reading a whole trace is expensive. A long agent run contains hundreds of spans and often hundreds of thousands of tokens. At frontier-model prices, most teams sample production traces. Failures outside that sample go unchecked.

We trained **flow-1** with reinforcement learning inside the Signals agent, using the same tools it has in production. The model treats a trace like a repository and each span like a file. It greps across spans, reads the relevant ones in full, and returns JSON that follows your schema.

We benchmarked it on 523 difficult traces from coding, legal, customer support, and CRM agents, with every model running inside the same Signals agent:

| Model | Detection F1 | Traces per $1 |
| --- | --- | --- |
| **flow-1** | **0.835** | **888** |
| Claude Opus 5 | 0.890 | 7 |
| Claude Sonnet 5 | 0.835 | 12 |
| GPT-6-sol | 0.816 | 38 |
| GPT-6-luna | 0.795 | 668 |

flow-1 ties Claude Sonnet 5 and beats GPT-6-sol on detection, at 74x and 23x lower cost per trace. Claude Opus 5 detects more, at 127x the cost. GPT-6-luna comes close on price and gives up 0.04 F1. Costs cover the full agent run, including every search and read, on traces under 100k tokens.

At this price, you can run a Signal on every trace. The [flow-1 announcement](https://laminar.sh/blog/flow-1) has the full benchmark, example outputs, and the gaps we're still working on.

</Note>

## Example: a redline that contradicts its own memo

A legal agent reviewed a counterparty's draft of a pharma partnership agreement. It had to deliver two files: a tracked-changes redline and an issues memo. The task required every issue in the memo to have a matching change in the redline.

Over 24 spans, the agent read eight source documents, then wrote the redline with one script and the memo with another. Both files passed the agent's own validation. Its final message read _"Completed and validated both deliverables."_

The two files disagree. The redline's new milestone section lists eight payments that add up to \$210M. The memo values the deal at \$457M, counting \$190M of milestones. It also states that every issue it lists has a corresponding change in the redline.

The **prompt** is one sentence:

```text wrap
Flag deliverables whose parts contradict each other: a summary figure that differs from the body, a date, amount or party name that changes between sections, or a conclusion that does not follow from the analysis presented.
```

The **output schema** asks for two fields, `first_statement` and `conflicting_statement`. This is the event, with flow-1's summary of the trace word for word:

```json wrap
{
  "summary": "The issues memo states the milestone total is $190M and the aggregate deal value is $457M, but the redline's milestone ladder sums to $210M, making the aggregate $477M.",
  "severity": "critical",
  "payload": {
    "first_statement": "Redline §5.2 lists eight milestone payments: $10M, $15M, $25M, $40M, $20M, $20M, $30M and $50M, a total of $210M.",
    "conflicting_statement": "The issues memo gives a $457 million aggregate value: $75M upfront + $190M milestones + $192M estimated cost share."
  }
}
```

Neither number appears in the final message. Each is in the input of a different `bash` span: the scripts that built the two files. To find the mismatch, flow-1 opened the full redline script, added up the milestone ladder, and compared it with the figure in the memo.

Run this Signal on every trace to get one row per affected trace. Each row is [queryable](/platform/sql-editor) in SQL and [clustered](/signals/clusters) with other runs whose deliverables disagree. You can configure an [alert](/signals/alerts) for the next occurrence.

## Anatomy of a Signal

You configure four parts of a Signal:

- **Prompt**: plain-language instructions describing what to detect or extract from a trace.
- **Structured output schema**: a JSON schema that the extracted payload must conform to. You name the fields to extract from every match, so you can filter and query events by those fields.
- **Trigger**: when Laminar reads the trace. By default, it runs when the trace finishes.
- **Filters**: which traces the Signal analyzes. Use them to exclude traces you don't need to inspect. The default is more than 1000 tokens.

Laminar handles the model, trace compression, and agent loop.

## What else Signals can help you answer

Beyond contradictions between deliverables, teams use Signals to track:

- **Business outcomes**: "agent completed checkout," "agent answered the question correctly."
- **Logical failures**: "agent loops on the same tool without progress," "agent gave up after one retry."
- **Behavioral categorization**: user intent, topic, any categorical field you want on the trace.
- **User friction**: "user asked for the same information multiple times," "user gave up after multiple retries."
- **Cost and waste**: "long context, short answer," "tool called with malformed arguments and retried."

Use a Signal for **anything you'd ask a teammate to find by reading traces**. A Slack request that starts with "can you look through today's runs and tell me how often..." can become a Signal prompt.

## How a Signal run works

A Signal run investigates the trace across multiple steps, using tools to search and read spans.

<Frame>
  <img src="/images/signals/signal-run.svg" alt="How a Signal run works: the trace is compressed into a transcript, an agent searches it and reads full spans before submitting its finding, and the finding becomes a signal event that feeds alerts, clusters, and SQL." />
</Frame>

### 1. The trace is compressed

A single agent run can contain hundreds of spans, megabytes of tool output, and the same system prompt repeated on every LLM call. Before the Signals agent sees the trace, Laminar renders it as a compact transcript:

- **The user's request goes first**, so the Signals agent knows what your agent was asked to do. Earlier conversation turns remain as context.
- **LLM turns and tool calls are kept**, with subagents grouped under the call that started them.
- **Each system prompt appears once** instead of on every turn. Long system prompts are summarized.
- **Other spans are dropped** unless they carry an error or your prompt names them.

Short traces go in whole. For longer traces, Laminar cuts oversized span inputs and outputs from the middle. Each cut is marked so the agent knows there is more to read. The user's request, system prompts, and errors are never cut.

### 2. An agent investigates the trace

An **agent with tools** follows your prompt and investigates the transcript across multiple steps. It accesses each span's input and output like files in a repository:

- **grep** runs a regex across every span, or a single one, and returns the matching snippets.
- **read** opens a span's full input or output, a page at a time.
- **submit** records what the agent found and ends the run.

A checkout failure in step 40 of a 200-step run remains accessible after truncation. The agent greps for it, reads the exact tool output, and quotes it in its answer. We instruct it to state only what the trace shows. Finding nothing is a valid result.

A run ends in one of two ways:

- The agent submits a **finding**: a payload that conforms to your schema, a short summary, and a severity. **Critical** means the result is wrong or unusable, or the agent broke a promise to the user. **Warning** is a localized defect. **Info** has no effect on the outcome, such as an extracted value or a category. Severity rules in your prompt override these defaults.
- The agent decides the behavior **isn't present**. Laminar creates no event.

On live traffic, each Signal runs once per trace, and every run produces at most one event. If the behavior occurs several times, such as a broken tool retried three times, the agent includes every occurrence in that event, with a summary for each.

### 3. The finding becomes a signal event

Laminar stores the finding as a **signal event** linked to its source trace. Span references in the payload become links into the trace. Laminar then processes the event:

- It **indexes the event for search**, so you can find it in the Signals UI.
- On live runs, it checks the event against your **alert rules** (severity and payload filters). Matching events fire [Alerts](/signals/alerts). Backfills don't send alerts.
- It queues the event for **clustering**, which groups similar events from other traces into [Clusters](/signals/clusters) so you can identify patterns.

<Note>
  Every event is queryable in the [SQL Editor](/platform/sql-editor), from either end. The `signal_events` table has one row per event. The `traces` table carries a trace's events and clusters as columns, so you can filter runs by what a Signal found and read cost, duration, and metadata off the same row.
</Note>

## Run a Signal on new traces or historical traces

Each Signal can run in two ways, configured independently:

- **Live**, on new traces as they arrive. Live runs feed dashboards and [Alerts](/signals/alerts).
- **Backfill**, across a historical slice of traces you select. Use a backfill to seed a new Signal, re-run a changed prompt over last week's traffic, or investigate traces you've already collected. A backfill reads every trace you select, regardless of trigger and filters.

Both produce the same kind of signal event.

For live runs, configure when the Signal runs and which traces it reads:

- The **trigger** determines *when* Laminar reads the trace. Every Signal has exactly one. **When a trace finishes** (the default) runs once the trace stops receiving spans, so the Signal sees the complete run. **When a specific span finishes** fires when a named span ends. Use it when the work is spread across services.
- **Filters** determine *whether* Laminar reads the trace. They apply to the whole trace, and every filter must match. You can filter by a minimum token count (a new Signal starts at more than 1000 tokens), an error status, a span name that appears anywhere in the run, or a tag. A Signal with no filters runs on every trace its trigger fires for.

The span-name trigger and the span names filter serve different purposes. The trigger names the span whose completion fires the Signal. The filter checks whether a span with that name appears anywhere in the trace.
