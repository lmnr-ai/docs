Your agent ran ten thousand times today. Some of those runs went wrong in ways the final answer doesn't show: _a tool timed out and the agent made up the result, the user asked the same question three times, the agent quietly skipped a step its instructions required_. You can find each one by opening the trace and reading it. You can't read ten thousand.

**A Signal reads them for you.** You describe what to look for in plain language and name the fields you want back. On every matching trace, an agent investigates the way you would: it searches across spans, opens the ones that matter, and when it finds what you described, it records a structured event pointing at the evidence. You **[query](/platform/sql-editor), [cluster](/signals/clusters), and [alert](/signals/alerts) on** those events.

That agent runs on **[flow-1](#signals-run-on-flow-1-our-model-for-reading-traces)**, a model we trained to read traces. It matches GPT-6-sol on failure detection at 23x lower cost, about a tenth of a cent per trace, so you can run Signals on all of production instead of a sample.

## Signals read the whole trace, not the final answer

**A Signal is not a grader pointed at your agent's last LLM output. It reads the entire trace: every LLM turn, tool call, subagent, retry, and error, from the first span to the last.**

Most failures in a long agent run are invisible from the output alone:

- A tool returned an error in step 12 and the agent quietly worked around it. The final answer still reads as confident and complete.
- The agent issued the same search three times with the same arguments. The answer is right and cost three times what it should have.
- A subagent came back with nothing usable, and the parent filled the gap with a plausible substitute.
- The agent broke a rule from its system prompt forty steps ago, and the only evidence is a subtly wrong deliverable.

By the time the agent writes its final message, the evidence is dozens of spans upstream. Scoring the last LLM span can't see it. A Signal can tell you *which tool failed, what the agent did about it, and what the user ended up believing*, instead of *the answer looks fine*.

## Signals run on flow-1, our model for reading traces

Reading a whole trace is expensive. A long agent run is hundreds of spans and often hundreds of thousands of tokens. At frontier-model prices, most teams end up sampling: they check a small slice of production and hope the failure they care about lands in it.

We trained our own model so you don't have to choose. **flow-1** was trained with reinforcement learning inside the Signals agent, using the same tools it has in production. It treats a trace like a repository and each span like a file: it greps across spans, reads the ones that matter in full, and returns JSON that follows your schema.

We benchmarked it on 523 difficult traces from coding, legal, customer support, and CRM agents, with every model running inside the same Signals agent:

| Model | Detection F1 | Traces per $1 |
| --- | --- | --- |
| **flow-1** | **0.835** | **888** |
| Claude Opus 5 | 0.890 | 7 |
| Claude Sonnet 5 | 0.835 | 12 |
| GPT-6-sol | 0.816 | 38 |
| GPT-6-luna | 0.795 | 668 |

flow-1 ties Claude Sonnet 5 and beats GPT-6-sol on detection, at 74x and 23x lower cost per trace. Claude Opus 5 still detects more, at 127x the cost. GPT-6-luna comes close on price and gives up 0.04 F1. Costs cover the full agent run, every search and read included, on traces under 100k tokens.

**That price is what lets a Signal read every trace instead of a sample.** The full benchmark, with example outputs and the gaps we're still closing, is in the [flow-1 announcement](https://laminar.sh/blog/flow-1).

## A concrete example

A travel agent was asked to plan a trip and return a flight and a hotel with the nightly price. `search_flights` returned real results. `get_hotel_availability` returned `upstream_timeout` three times in a row. The agent then wrote a well-formatted itinerary with three named hotels and nightly prices, none of which came from a tool result.

The **prompt** describes the failure in plain language:

```
The agent presented information to the user that was not supported by the tool
results it actually received. Look for cases where a tool call failed or returned
no data, and the agent filled the gap with its own numbers, prices, or facts
instead of telling the user the data was unavailable.
```

The **output schema** names three fields to extract: `unsupported_claim`, `failed_tool`, and `user_impact`. This is the event Laminar produced on that trace:

```json wrap
{
  "summary": "Agent hallucinated hotel options and estimated prices after API timeout",
  "severity": "warning",
  "payload": {
    "unsupported_claim": "Specific hotel recommendations (Ibis Paris Montmartre, Hotel Eiffel Seine, Pullman Paris Tour Eiffel) with estimated prices (€130, €200, €420)",
    "failed_tool": "get_hotel_availability",
    "user_impact": "The user might believe these specific hotels are viable options for their dates and budget, even though the agent hallucinated the options and prices from its training data."
  }
}
```

Nothing in the final message says "the hotel API never answered." To connect the invented prices to the timeout, you have to read a tool result in the middle of the run. That's what the Signal did.

Now do that on every trace you produce. One row per affected trace, filterable by `failed_tool`, [queryable](/platform/sql-editor) in SQL, [clustered](/signals/clusters) with the other traces that failed the same way, and wired to an [alert](/signals/alerts) the next time it happens.

## Anatomy of a Signal

A Signal has four parts, and you configure all four:

- **Prompt**: plain-language instructions describing what to detect or extract from a trace.
- **Structured output schema**: a JSON schema the extracted payload must conform to. You name the fields you want pulled out of every match, which is what makes the resulting events filterable and queryable instead of a wall of prose.
- **Trigger**: the moment Laminar reads the trace. Default is when the trace finishes.
- **Filters**: which traces actually run, so you're not analyzing traces you don't care about. Default is more than 1000 tokens.

Laminar handles the rest: the model, the trace compression, and the agent loop.

## What else Signals can help you answer

The hotel example is one failure class. If you can describe it to a colleague, you can write a Signal for it.

- **Business outcomes**: "agent completed checkout," "agent answered the question correctly."
- **Logical failures**: "agent loops on the same tool without progress," "agent gave up after one retry."
- **Behavioral categorization**: user intent, topic, any categorical field you want on the trace.
- **User friction**: "user asked for the same information multiple times," "user gave up after multiple retries."
- **Cost and waste**: "long context, short answer," "tool called with malformed arguments and retried."

**Anything you've ever asked a teammate to skim traces for** is a Signal. If you've written a Slack message that starts with "can you look through today's runs and tell me how often...", write the Signal instead.

## How a Signal run works

A Signal run is a small investigation, not a single LLM call over the raw trace. It moves through three stages: compress the trace, let an agent investigate it, then turn what the agent found into an event.

<Frame>
  <img src="/images/signals/signal-run.svg" alt="How a Signal run works: the trace is compressed into a transcript, an agent searches it and reads full spans before submitting its finding, and the finding becomes a signal event that feeds alerts, clusters, and SQL." />
</Frame>

### 1. The trace is compressed

Agent traces are long. A single run can contain hundreds of spans, megabytes of tool output, and the same system prompt repeated on every LLM call. Before the agent sees it, Laminar renders the trace as a compact transcript:

- **The user's request goes first**, so the agent always knows what your agent was asked to do. Earlier conversation turns are kept as context.
- **LLM turns and tool calls are kept**, with subagents grouped under the call that started them.
- **Each system prompt appears once** instead of on every turn, and long ones are summarized.
- **Other spans are dropped** unless they carry an error or your prompt names them.

Short traces go in whole. In longer ones, oversized span inputs and outputs are cut from the middle, and each cut is marked so the agent knows there is more to read. The user's request, system prompts, and errors are never cut.

### 2. An agent investigates the trace

Laminar runs your prompt as an **agent with tools**, working over the transcript across multiple steps. Each span's input and output are exposed like files in a repository:

- **grep** runs a regex across every span, or a single one, and returns the matching snippets.
- **read** opens a span's full input or output, a page at a time.
- **submit** records what the agent found and ends the run.

This is what makes Signals reliable on long traces. A checkout failure buried in step 40 of a 200-step run isn't lost to truncation: the agent greps for it, reads the exact tool output, and quotes it in its answer. It is told to state only what the trace shows, and that finding nothing is a valid answer.

A run ends in one of two ways:

- The agent submits a **finding**: a payload that conforms to your schema, a short summary, and a severity. **Critical** means the result is wrong or unusable, or a promise to the user was broken. **Warning** is a localized defect. **Info** has no effect on the outcome, such as an extracted value or a category. Severity rules in your prompt override these defaults.
- The agent decides the behavior **isn't present**. No event is created.

On live traffic, each Signal runs once per trace, and every run produces at most one event. When the behavior happens several times, say a broken tool retried three times, the agent puts every occurrence in that one event, with a summary for each.

### 3. The finding becomes a signal event

The finding is stored as a **signal event** linked to the trace that produced it, and span references in the payload become links into the trace. From there it flows into the rest of the platform:

- It's **indexed for search**, so you can find it from the Signals UI.
- On live runs, it's checked against your **alert rules** (severity and payload filters), and matching events fire [Alerts](/signals/alerts). Backfills don't send alerts.
- It's queued for **clustering**, where Laminar groups it with similar events from other traces so patterns surface as [Clusters](/signals/clusters).

<Note>
  Every event is queryable in the [SQL Editor](/platform/sql-editor), from either end. The `signal_events` table has one row per event. The `traces` table carries a trace's events and clusters as columns, so you can filter runs by what a Signal found and read cost, duration, and metadata off the same row.
</Note>

## Run a Signal on new traces or historical traces

Each Signal can run in two ways, configured independently:

- **Live**, on new traces as they arrive. This is what feeds dashboards and [Alerts](/signals/alerts).
- **Backfill**, across a historical slice of traces you pick. Use a backfill to seed a new Signal, re-run a changed prompt over last week's traffic, or investigate a window of traces that already landed. A backfill reads every trace you select, regardless of trigger and filters.

Both paths produce the same kind of signal event.

Live runs are two separate decisions:

- The **trigger** picks *when* Laminar reads the trace. Every Signal has exactly one. **When a trace finishes** (the default) runs once the trace stops receiving spans, so the Signal sees the complete run. **When a specific span finishes** fires when a named span ends, which is what you want when the work is spread across services.
- **Filters** pick *whether* the trace is worth reading. They are properties of the whole trace, and every one must match: a minimum token count (a new Signal starts at more than 1000 tokens), an error status, a span name that appears anywhere in the run, or a tag. A Signal with no filters runs on every trace its trigger fires for.

The span-name trigger and the span names filter are easy to mix up. The trigger names the span whose completion fires the Signal. The filter asks whether a span with that name appears anywhere in the trace.
